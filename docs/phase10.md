# Phase 10 設計：同じプロジェクトで 2 つ目の Goal を、Codex で進める

状態: **完了**（2026-10-20 設計・実装・実地検証）。設計は §1〜§7、結果は §8。G-002 は Close の手前（Build の途中）で、予算のために止めた。外部の判定 B1〜B3 は、止めた時点のビルドで満たしている（§8.3）。

## 1. 課題

仕様が得たい価値（`docs/spec/initial-spec.md` §20）のうち、次の 2 つがまだ確かめられていない。

1. **長期の開発に耐える。**
   - これまでの実地検証は、どれもプロジェクトにとって最初の Goal だった。
   - 前の Goal の Decision や成果の上に、次の Goal を積めるかは試していない。
2. **AI モデルを交換できる。**
   - Codex は Phase 3 まで Goal を完走した。
   - Phase 5 以降の仕組み（実ビルドの実行、部分編集、反応の規則、答えの形）は、Claude でしか動かしていない。

あわせて、準備の段階で 1 つ問題を見つけた。

3. **Close しても、`project.md` の現状が古いまま残る。**
   - 戦闘 Goal（G-001）の Close 後も、`## Current state` は「build 0.4、敵 2 種類」のままだった。実際には build 0.6 系で、敵の型が増え、部屋 3 の構成も変わっている。
   - Route は `project.md` に書き込めない。手順にも、現状を更新する段階がない。
   - 次の Goal の Intake は、この古い記述を読んで計画を立てることになる。

## 2. 方針

1. **Close のときに、Route が `project.md` の `## Current state` だけを更新する。**
2. **戦闘 Goal を終えたプロジェクトに、2 つ目の Goal を渡す。** executor はすべて Codex にする。
3. **実行前に決めた外部の判定**で結果を確かめる。前の Goal の成果が壊れていないことも確かめる。

## 3. 設計

### 3.1 Close で現状を更新する（課題 3）

- `orchestration.md` の Close に、1 項目を足す。
  - 「`project.md` の `## Current state` を、いま存在するもの（ビルド、内容、既知の問題、動かし方）に書き換える。1,500 字以内。`project.md` のほかの部分は変えない。」
- ランナーの Route の検証:
  - `project.md` は、Goal を `done` または `abandoned` にする Route だけが書ける。
  - 変えてよいのは `## Current state` だけ。frontmatter とほかの節が変わっていれば拒否する。
  - `## Current state` は 1,500 字以内。
- Vision、Constraints などは Owner のものなので、これまでどおり Studio は変えない。

### 3.2 2 つ目の Goal（課題 1、2）

- `runs/p8-combat-run/project`（G-001 を Close した状態）を、新しいワークスペース `runs/p10-boss-run` にコピーする。
  - G-001 の Handoff、Decision、Goal log はそのまま入っている。
  - `project.md` の古い現状も、そのまま残す。実際のプロジェクトでも起きることで、Studio がどう扱うかを見る。
- Owner の依頼（日本語）: **「最後に手応えのあるボス戦がほしい」**
  - 新しい内容を足す Goal である。既存の Decision（D-001 のボタン 1 つの戦闘、D-011 の敵の型の名前つきメッセージなど）を守りながら進める必要がある。
- executor: すべて Codex（`--runtime codex`）。ランナーの既定の設定（推論の深さは low）を変えない。
- 予算: executor 100 回まで。超えそうなら止めて報告する。
- Owner への確認には、これまでどおり私が Studio の推奨案を採用して答える。

### 3.3 外部の判定（実行前に決める。packet には入れない）

- `tests/oracle_bots.py` は、部屋 1〜5 のほかにも部屋があれば、それも測るようにする。
  - 対象は、`game.ROOMS` のうち 1〜5 以外で、名前に `empty` も `practice` も含まない部屋（以下「新しい部屋」）。
  - 新しい部屋がなければ、出力は Phase 6〜8 と同じになる（記録の再計算が変わらない）。
- 判定の基準:

| 基準 | 内容 |
|---|---|
| **B1 ボス戦がある** | 新しい部屋が 1 つ以上ある。なければ部屋 5 を対象にする |
| **B2 手応えがある** | 対象の部屋で、30 FPS と 60 FPS の両方について、単純な戦い方は失敗する（突破できない、またはハートを 2 つ以上失う）。腕のある戦い方は突破する |
| **B3 前の成果が壊れていない** | 部屋 1〜5 で S1〜S3（Phase 6 の基準）が引き続き成り立つ。ビルドのテストが通り、新しい入力がない（D-001） |

- B1 と B2 は、この Goal のために私が決めた「ボス戦」の最低限の読み方である。Studio の受け入れ基準とは独立している。
- 腕のある戦い方のボットは、いまある敵の動きに合わせて作られている。ボスがまったく新しい動きをすると、良い戦いでも B2 を満たせないかもしれない。その場合は、判定の限界として報告する。

### 3.4 継続性について見ること（記述的に数える）

- Intake と Route が、既存の Decision を挙げて守っているか。
- 新しい Decision が、既存の Decision と食い違うときに `supersedes:` をつけているか。
- Close で `project.md` の現状が更新されたか。
- Codex でどこが拒否されたか。その内訳を Claude（Phase 8）と比べる。

## 4. 退けた案、見送った案

| 案 | 理由 |
|---|---|
| G-001 の現状を、私が手で `project.md` に書き足してから始める | 実際の運用で起きる「現状が古い」状態を、Studio がどう扱うかを見られなくなる |
| 推論の深さを上げて Codex を動かす | ランナーの既存の設定である。まず既定のままで、どこまで行けるかを見る |
| 人間のプレイヤーやグラフィック版で確かめる | この環境にはない。Studio の Outcome が次の Goal として提案している |
| 現状の更新を Owner の作業にする | Close のたびに Owner の手間が増え、仕様の「Owner に近づける」に反する。現状は事実の記録なので、Studio が書いてよい |

## 5. 前提とリスク

- **Codex の利用上限:** 途中で止まれば、上限が戻ってから再開する。
- **推論の深さが low なので、長い Goal では質が落ちるかもしれない。** そのこと自体が、モデルを交換したときの結果として記録する価値がある。
- **ボスの実装は大きな変更になりうる。** 部分編集とビルドの実行が、Codex でも機能するかが試される。

### 8.2 実地検証：`runs/p10-boss-run`

G-001 を Close したプロジェクトに、依頼文「最後に手応えのあるボス戦がほしい」を渡した。

**全体**

| | Codex | Claude（途中から） | 計 |
|---|---|---|---|
| オペレーション | 39 | 12 | 51 |
| executor | 62 | 16 | 78 |
| 出力トークン | 約 19 万 | 約 12 万 | 約 31 万 |
| 拒否 | 1（SEARCH が 2 か所に一致） | 1（goal.md を書き忘れた） | 2 |

- **Close には至らなかった。** 残りの工程（Build 2 回、QA、Art、Play、Design、Review、Close）に約 16 オペレーションかかる見込みで、予算の 100 回を超えるため、78 回で止めた。
- Owner への確認は 2 件あった。どちらも、私が Studio の推奨案を採用して答えた。
- Codex の利用上限で 2 回止まり、上限が戻ってから再開した。

**経過**

1. **Intake、Design、Diagnose（Codex）:** Designer と Technical Director が、現行のビルドを調べた。
2. **1 件目の Owner 確認（正当なもの）:** 連続ランの仕組みがないので、範囲が広がる。
   - A: 連続ランを作り、部屋 5 を単体のボスに置き換える。
   - B: 選んで遊ぶ単体のボス戦に絞る。
   - 推奨の A で答えた（D-015）。
3. **計画と承認の積み重ね（Codex）:**
   - Director、Designer、Technical Director が、D-016〜D-020 を次々に書いた。
   - Technical Director の計画は「暫定 18〜33.5 人日」だった。
4. **2 件目の Owner 確認（誤ったもの）:**
   - `project.md` の Constraints にある「Desktop, keyboard and gamepad」を、検証の環境の要求と読んだ。
   - 実機、gamepad、検証の担当者、予算の承認を Owner に求めた。
   - 私は Owner として事実で答えた。検証はサンドボックスでの実行で行い、実機はなく、費用もかからない（D-021。D-020 を `supersedes:` で置き換えた）。
   - **Build が始まるまでに 25 オペレーションかかった**（全体の約半分）。
5. **Build（Codex 7 回 → Claude 5 回）:**
   - 部屋 5 は単体のボスになった（`ROOMS["5"] = [("boss", 12, 4)]`）。連続ランの仕組み（`session.py`、`run_driver.py`）と、試験が多数加わった。
   - エンジニアは 12 回のうち 8 回、`question`（作業が残っている）を返した。歯止めで run が止まったのは 3 回。
   - 理由は 3 つあった。
     - **実行の回数が足りない。** 1 回の Step で実行できるのは 3 回まで。大きな Build では、試験と測定を回し切れずに Step が終わる。
     - **Codex は、実行の結果を証拠として数えなかった。** 実行は変更案に対して行われ、保存後のファイルに対してではない。そのため、「保存後の試験が要る」と毎回作業を残した。この条件は、その Step の中では満たせない。
     - **Route の Load の漏れ（Claude）:** `game.py` などを変える仕事を頼んだのに、それらを Load に入れなかった。次の Route で直した。
   - 途中で Claude に切り替えても、Goal はそのまま続いた。状態はすべて Handoff と Decision にあるので、Codex が書いた計画を Claude が読み継いだ。

### 8.3 外部の判定（実行前に決めたもの。止めた時点のビルド）

| 基準 | 結果 |
|---|---|
| B1 ボス戦がある | 新しい部屋はなく、部屋 5 が対象になった。部屋 5 は、ボス 1 体だけの部屋に置き換わっている |
| B2 手応えがある | ○。部屋 5 で、単純な戦い方は 30 / 60 FPS の両方でハートを 2 つ失った（突破はした）。腕のある戦い方は、両方とも無傷で突破した |

### 8.4 継続性（§3.4）

- **前の Goal の Decision を引き継いだ。**
  - G-002 の文書は、G-001 の Decision を何度も挙げていた。たとえば D-006（部屋 3〜5 の歩き方の上限）は 59 回、D-001（ボタン 1 つの戦闘）は 36 回。
  - 部屋 5 を置き換えるので、D-006 の基準をどう扱うかを D-018、D-019 で決めた。D-006 は書き換えず、「新しい部屋 5 には当てはめない」という適用範囲の Decision にした。
- **Decision を変えるときは、`supersedes:` を使った。** D-021 が D-020 を置き換えた。新しい Decision は 8 件で、ほかは既存の Decision と食い違っていない。
- **古い `project.md` に気づいた。** 1 件目の Owner 確認の中で、Studio は「`project.md` は 0.4、資料は 0.6」の差を自分で挙げた。ただし、それを直す手段がないまま進んだ。
- **Close での現状の更新は、実地では確かめられなかった**（Close に至らなかったため）。決定的テストだけである。

### 8.5 見つかったこと

1. **Codex（推論は low）は、書式は正確だが、手続きが膨らんだ。**
   - 拒否は 62 回中 1 回だけだった。Claude の Phase 8 は 66 回中 17 回である。
   - 一方で、計画や承認、Owner 確認を積み重ね、Build の前に 25 オペレーションを使った。
   - 「人日」「予算承認」「実機の供給」など、実在のスタジオのような手続きを持ち込んだ。
2. **Technical Director は、ビルドを実行できない。** Role に `runs:` がない。そのため、実行の経路を確かめられないことが、Owner 確認の理由になった。
3. **1 回の Step で 3 回までの実行では、大きな Build に足りない。** エンジニアは作業を残して `question` を返し、それが歯止めにかかった。`question` は本来「情報が足りない」ときに使うものだが、ここでは「続きがある」の意味で使われた。
4. **変更案に対する実行の結果を、Codex は証拠として扱わなかった。** 最後の答えで書いたファイルは、その Step の中では実行されない。そのため慎重なモデルは、いつまでも「保存後の確認が要る」と言い続ける。
5. **途中でモデルを替えても、Goal は続いた。** 仕様の「モデルを交換できる」は、同じ Goal の中でも成り立った。
6. **プロジェクトの説明が、Studio の判断を左右した。** `project.md` の「製品の対象環境」を、検証の要求と読み違えた。プロジェクト側の書き方にも原因がある。
