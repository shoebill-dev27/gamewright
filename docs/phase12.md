# Phase 12 設計：読めない Load を拒否し、Step も足りない本文を求められるようにする

状態: **設計**（2026-10-22。Owner の指示「私が判断しないといけないこと以外は止まらずにそっちで判断して進めて」により、承認待ちで止めずに実装する）

## 1. 課題（Phase 11 の実測。`runs/p11-boss-run`、`docs/phase11.md` §8.4）

1. **Load の一覧に書いたディレクトリが、黙って捨てられた。**
   - QA への Handoff（57）の Load に `repo/` と書かれていた。
   - ランナーはファイル名しか拾わないので、それを読み飛ばした。QA は、12 個のテストファイルの本文を 1 つも受け取れなかった。
   - Route にも QA にも、エラーは出なかった。
2. **Step は、足りない本文を自分で求められない。**
   - Route は `@need` で 1 回だけファイルを追加で求められるが、Step にはその手段がない。
   - QA は本文の不足を 2 回報告し、それが Owner への確認（G-002 で 3 件目）になった。
3. **executor は、packet の外に環境や人や予算があると考えて、Owner に求める。**
   - G-002 の Owner 確認 3 件のうち 2 件がこれだった。1 件目は実機、gamepad、予算。もう 1 件は、全文のログの保存先と独立した実行の枠。
   - executor への指示には「packet の外のことを仮定しない」とあるが、「packet の外には何もない」とは書いていない。
4. **G-002 が Close していない。**

## 2. 方針

1. Load にディレクトリが書かれていたら、中のファイル名を packet に並べる（実装中に、拒否から変えた。§3.1）。
2. Step も、1 回だけ `@need` でファイルを追加で求められるようにする。そのとき、受け取る Role の読み込みのポリシーで確かめる。
3. executor への指示に、「packet と、そこで使える実行のほかには何もない。Owner にも求めない」と書く。
4. 3 件目の Owner 確認に答え、G-002 を Close まで進める。

## 3. 設計

### 3.1 Load のディレクトリ（課題 1）

**実装中に変えた。** 当初は、Load にディレクトリが書かれていたら拒否する設計だった。

- ところが、記録の Handoff を確かめると、Route は「the build in repo/ (run with …)」という書き方をいつも使っていた。「このビルドは実行で使う」という意味の注記である。QA 57 の `repo/` も、この種の注記だった。
- 拒否にすると、ふつうの Handoff がエラーになる。記録の Handoff を検証するテストも失敗した。

そこで、拒否はせずに、**中のファイル名を packet に並べる**ことにした。

- Step の packet で、Load の節にある「`/` を含む語」のうちプロジェクトに実在するディレクトリを指すものは、中のファイル名を `@files/<ディレクトリ>` として入れる。
  - 入れるのは名前だけで、本文は入れない。
  - 受け取る Role が読んでよいファイルに限る。Playtester には、ゲームのソースの名前も見せない。
  - 最大 80 件まで。
- 受け取った Step は、必要な本文を `@need`（§3.2）で求められる。
- 実在しない語（文の中の `and/or` など）は、今までどおり無視する。

### 3.2 Step の `@need`（課題 2）

- Step も、最終的な答えの代わりに 1 回だけ `@need` ブロックを書ける。中身は、最大 8 個のプロジェクトのファイルか Studio のファイル。
  - ランナーはそれを packet に足し、新しい executor でもう一度実行する（Route と同じ）。
- **受け取る Role のポリシーで確かめる。**
  - `load_only`、`load_forbid` に反するファイルは拒否する。たとえば、Playtester はゲームのソースを求められない。
  - Handoff を求めた場合は、`strip_sections`（Sender assessment など）を除いて渡す。
- 実行要求（run round）の後でも使える。足したファイルは、次の実行要求の後も packet に残る。
- `execution.md` の「Context request」の節を、Route と Step の両方について書き直す。

### 3.3 packet の外には何もない（課題 3）

- `execution.md` の executor への指示に、1 項目足す。
  - 「この packet と、そこで使える実行（`@run`）、ファイルの追加要求（`@need`）のほかには、環境、人、機器、予算、ログの保存先はない。それらを Owner に求めない。手元の手段で確かめられないことは、確かめられないと書く。」
- ツールの名前を出さない書き方にする（`studio/` の規則）。

### 3.4 G-002 を Close まで（課題 4）

- `runs/p11-boss-run` を `runs/p12-boss-run` にコピーして続ける（記録 077 以降が Phase 12）。
- 3 件目の Owner 確認には、推奨の案 A を採り、供給の事実を答える。
  - 本文は `@need` と Load で渡す。
  - 実行は 1 回の Step で 3 回まで。
  - 実行結果は 2 万字まで（先頭と末尾）。全文の保存先はない。
  - 変更前のビルドは保存されていない。
- executor: Codex。利用上限で止まったら、戻るのを待って再開する。
- 予算: executor を 45 回追加（合計 149 回まで）。
- Close したら、`project.md` の現状の更新と、B1〜B3 を確かめる。

## 4. 退けた案、見送った案

| 案 | 理由 |
|---|---|
| Load のディレクトリを展開して、中のファイルを全部入れる | packet が大きくなりすぎる。テストのディレクトリだけで 12 ファイルある。必要なものを選ぶのは Route の仕事 |
| 実行結果の上限（2 万字）を上げる | packet が大きくなる。必要な行に絞るスクリプトを書けば足りる |
| `@need` を何度でも使えるようにする | packet が際限なく大きくなり、Step が終わらなくなる |

## 5. 前提とリスク

- `@need` の要求は、executor を 1 回余分に使う。ただし、Owner 確認や Step のやり直しよりは安い。
- 実行要求の後の packet はもともと大きい。そこにファイルを足すと、さらに大きくなる。8 ファイルの上限で抑える。
