# Phase 14 設計：新しい Goal を、最初から予算つきで動かす

状態: **完了**（2026-10-23 実地検証）。結果は §4。G-003 は予算の見込み（9）を 4 上回る 13 オペレーションで Close した。

## 1. 課題

- Phase 13 で予算の仕組みを入れた。しかし実地で試したのは、予算なしで 78 オペレーションを使った後の G-002 だけである。予算は、最初から超過していた。
- 本来の使い方は、Intake が最初に見積もり、Route がそれを見ながら進むことである。これは、まだ確かめていない。
  - Intake は、妥当な予算を書けるか。
  - Route は、予算の内側で Close に向かうか。
  - 超えそうなとき、早めに範囲か費用の判断をするか。

## 2. 方針

- コードは変えない（問題が見つかれば直す）。
- G-002 を閉じたプロジェクトに、3 つ目の Goal を渡す。依頼は小さめにする。
  - 依頼文: **「ダッシュがいつまた使えるのか分かりにくい。分かるようにしてほしい」**
  - ダッシュには 0.6 秒の待ち時間（`DASH_COOLDOWN`）があるが、プレイヤーの画面にそれが出ているかは、Studio が調べることになる。
- executor: Claude（Sonnet）。Codex は利用上限のため使えない。
- 実行の予算: executor 60 回まで。
- Owner への確認には、これまでどおり私が推奨案で答える。

## 3. 見ること

- Intake が書いた `budget:` と、計画した工程の数。
- Close までに使ったオペレーションの数と、予算との比較。
- 予算を超えそうになったときの Route の動き（超えなければ、その旨を書く）。
- Close での `project.md` の現状の更新と、G-001・G-002 の Decision の引き継ぎ。
- 外部の判定 S1〜S3、B1〜B2 が崩れていないか（D-001 のボタン 1 つの戦闘を守るか）。

## 4. 結果：`runs/p14-budget-run`（Claude、Sonnet）

### 4.1 全体

- **Close に至った。**
  - 13 オペレーション、executor 24 回、出力約 13 万トークン。
  - Owner 確認は 0 件。
  - 拒否は 3 回で、どれも 1 回のやり直しで通った。全体とファイルの編集の混在、Load の場所の誤り、Playtester に読めないファイルを渡したもの、の 3 つである。
- **予算:**
  - Intake の見込みは 9、実際は 13（G-003 のオペレーションの数）。
  - 予算を超えた後の Route は 2 回あった。どちらも工程を足さずに、計画済みの Play と Close へ進んだ。予算の規則による拒否は出なかった。
  - 超えた 4 の内訳は、1 回の戻りである。最初の Build のランナーの試験が失敗し、Design の決定（D-028）と Build の修正にもう一度回った。
- **継続性:**
  - G-001 と G-002 の Decision を引き継いだ。たとえば D-001 のボタン 1 つの戦闘は守られ、新しい入力はない。
  - Close の Route は、`project.md` の `## Current state` だけを書き換えた。G-003 の変更、試験の数、既知の問題（部屋 3 の狙い線の重なり、G-002 の打ち切り）が書かれた。

### 4.2 経過

1. **Intake:**
   - Observe と Plan を省いた。Owner の報告で問題がはっきりしており、変更も局所的だったため。
   - Diagnose と Design を Designer の 1 工程にまとめ、予算を 9 とした。
2. **Design:** Designer がプレイヤーの表示を実行して、ダッシュの状態が画面に出ていないことを確かめ、仕様を書いた。
3. **Build:**
   - エンジニアは `@need` でソースを求めて実装した。
   - ランナーの試験は exit 1 だった。Route は Designer に決定を求めた（再充電は 0.85 秒、ダッシュの終わりから数える、など。D-028）。
   - 2 回目の Build は exit 0 だった。
4. **Verify:** QA は、30 / 60 FPS の両方で不合格を出さなかった。旧ビルドの出力がないので、DR8 と DR9 の一部は未検証として残した。
5. **Play:** Playtester は部屋 1 と 3 で、表示とメッセージ、実際に再び使えるようになる時刻が一致することを確かめた。部屋 3 では、スピッター 3 体の狙い線が重なって読みにくいことも報告した。
6. **Close:** Review は省いた。Play の結果が Goal について明確で、方向を変える要素がなかったため。Outcome に次の Goal の案を 3 つ挙げた。

### 4.3 外部の判定

- S1〜S3、B1〜B2 をすべて満たす。
- 数値は Phase 13 と同じだった。表示の変更なので、遊びの中身は変わっていない。

### 4.4 見つかったこと、直したこと

1. **予算は、小さな Goal では邪魔をしなかった。** 見込みを超えた後も、計画済みの工程には進めるので、Close まで行けた。
2. **Intake の見込みは、戻りの分が少なかった。**
   - 「戻り 1 回分の余裕」が 1 オペレーションと読まれていた。
   - 実際の戻り（Design と Build）は 4 オペレーションかかった。
   - そこで、`orchestration.md` の目安を具体的にした。「工程ごとに 2、2 工程を通る戻り 1 回に 4、Intake に 1」。この式なら、G-003 の計画（Design、Build、Verify、Play）は 2×4＋4＋1＝13 になり、実際と一致する。
3. **Codex との比較はしていない。** Codex は利用上限のため使えなかった。G-002 の計画が膨らんだのは Codex のときだったので、同じ依頼を Codex で試せば比べられる。
