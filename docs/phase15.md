### 4.2 経過

1. **Intake:** Diagnose、Design、Build、Verify、Play、Review を計画した。予算は 17。
2. **Diagnose と Design（Designer 2 回）:**
   - Designer がプレイヤーの表示を実行して、ダッシュの状態が画面に出ていないことを確かめた。
   - 仕様を書いた（D-028）。
3. **1 回目の Build（無駄になった）:**
   - Route が、Load にゲームのソースを 1 つも入れなかった。
   - エンジニアは、ファイル名が分からないまま `@need` で推測した（`driver.py`、`view.py`、`engine.py`）。どれも存在せず、拒否された。
   - 2 回目の `@need` で一部を得たが足りず、作業せずに `partial` で返した。
   - Route が、ソースを Load に入れて開き直した。ここで 2 オペレーションを使った。
4. **2 回目の Build:** ランナーの試験は exit 0 だった。
5. **Verify:**
   - 表示そのものは正しかった。
   - ただし、30 FPS では再び使えるまで約 0.9 秒かかり、仕様の 0.85 秒とずれることを見つけた。
6. **Design（D-029）と Build:**
   - Designer は、ダッシュの性能は変えず、30 FPS では「0.9 秒後」と表示・説明するのが正しいと決めた。
   - エンジニアが表示と説明書を直した。試験は 180 件が通った。
7. **QA と Play を並行して実施:**
   - QA は不具合を見つけなかった。Playtester は、ダッシュの状態と残り時間を読み取れた。
8. **Review（予算を使い切った時点）:**
   - Route は、予算の残りを見て、Review を「判定と範囲の絞り込み」として開いた。
   - Director は達成と判断した。未確認の項目は、次の Goal に回した（D-030）。
9. **Close:** `project.md` の `## Current state` だけを書き換えた。

### 4.4 見つかったこと、直したこと

1. **ビルドを書く Role に、ビルドのファイル名を必ず見せる。**
   - 1 回目の Build が無駄になった原因は、Route がソースを Load に入れなかったことと、エンジニアがファイル名を知らなかったことである。
   - Phase 10 の G-002 でも、Route が変更するファイルを Load に入れ忘れたことがある。
   - そこで、ビルドを書く Role（エンジニア）の Step の packet には、Load に何が書かれていても、ビルドのファイル名の一覧（名前だけ）を必ず入れるようにした。エンジニアは、正しい名前を `@need` で求められる。
2. **予算は、最後の工程の形を変えた。**
   - 予算を使い切る直前の Route は、Review を「判定と範囲の絞り込み」として開いた。
   - Director は、未確認の項目を Goal の外に出して、達成と判断した。予算が、Goal の終わり方を自然に絞った。
3. **同じ依頼でも、経過のばらつきが大きい。** 13 と 20。予算の目安の効果をきちんと測るには、同じ依頼を何回か動かす必要がある。
