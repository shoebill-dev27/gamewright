## 1. 課題

- これまでの実地検証は、どれも**すでにビルドがあるプロジェクト**に Goal を渡すものだった。戦闘を改善する、不具合を直す、ボスを足す、表示を足す、などである。
- 実際のプロジェクトの始まりは、コンセプトだけがあってビルドがない状態である。そこから Studio が次のことをできるかは、まだ確かめていない。
  - 設計、計画、最初の実装、試験の土台、説明書を作ること。
  - 遊べる最初の版で Close すること。

## 3. コンセプト：Lamplight Keeper（灯台守）

- **どんなゲームか:** 岩の多い海岸の灯台を、一晩ずつ守るターン制のパズル。
  - 暗い海から船が 1 ターンに 1 マスずつ、港へ向かって来る。
  - 灯台の光を当てた船は、進路を変える。
  - 船を港に入れ、岩に当てないようにする。
- **柱:**
  1. 1 ターンの選択は 1 つだけ。光を左に回す、右に回す、そのまま。
  2. 先読みが楽しさ。数ターン先の船の位置と、光の効き方は、画面から読める。運では決まらない。
  3. 一晩は短い。数分で勝つか負ける。
- **制約:**
  - Python 3 の標準ライブラリだけで作る。入力のスクリプトで遊び、文字の格子で表示する。
  - 同じスクリプトなら、いつも同じ結果になる。
  - 実行のコマンド（`run_play`、`run_trace`、`run_tests`）は `project.md` で決めてある。スクリプトの書式はビルドが決め、`repo/manual.md` に書く。
- `repo/` には README だけがある。設計書も Decision もない。
- 数値（盤の大きさ、船の数、光の幅、ターン数）や細かなルールは、すべて Studio が決める。

## 4. 外部の判定（実行前に決める。packet には入れない）

Close の後に、私が `repo/manual.md` だけを読んで、人間のプレイヤーと同じ立場で遊んで判定する。

| 基準 | 内容 |
|---|---|
| N1 遊べる | 説明書に書かれた書式だけでスクリプトを書き、`run_play` で一晩を最後まで遊べる |
| N2 作りが制約どおり | `run_tests` が通る。標準ライブラリだけを使っている |
| N3 選択に意味がある | 同じ夜で、勝てる手順と負ける手順の両方がある。手順を全通り試せる長さなら、`run_play` を使って総当たりで確かめる |
| N4 決定的 | 同じスクリプトを 2 回遊ぶと、出力が完全に同じになる |
| N5 柱 1 を守る | プレイヤーの操作は「左、右、そのまま」だけ |

- N3 の総当たりは、ビルドの内部ではなく、プレイのコマンドだけを使う。
- 「楽しいか」は判定しない。Studio の Play と Review の報告を、そのまま記録する。
