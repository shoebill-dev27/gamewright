## 3. コンセプト：Lamplight Keeper（灯台守）

- **どんなゲームか:** 岩の多い海岸の灯台を、一晩ずつ守るターン制のパズル。
  - 暗い海から船が 1 ターンに 1 マスずつ、港へ向かって来る。
  - 灯台の光を当てた船は、進路を変える。
  - 船を港に入れ、岩に当てないようにする。
- **柱:**
  1. 1 ターンの選択は 1 つだけ。光を左に回す、右に回す、そのまま。
  2. 先読みが楽しさ。数ターン先の船の位置と、光の効き方は、画面から読める。運では決まらない。
  3. 一晩は短い。数分で勝つか負ける。
- **制約:**
  - Python 3 の標準ライブラリだけで作る。入力のスクリプトで遊び、文字の格子で表示する。
  - 同じスクリプトなら、いつも同じ結果になる。
  - 実行のコマンド（`run_play`、`run_trace`、`run_tests`）は `project.md` で決めてある。スクリプトの書式はビルドが決め、`repo/manual.md` に書く。
- `repo/` には README だけがある。設計書も Decision もない。
- 数値（盤の大きさ、船の数、光の幅、ターン数）や細かなルールは、すべて Studio が決める。

### 6.2 経過

1. **Intake:**
   - Design → Build → Verify → Play → Review を計画した。
   - Plan（Technical Director）は省いた。標準ライブラリだけで作る小さなビルドなので、計画の工程は要らないと判断した。
   - 予算は 15 とした。
2. **Design:**
   - Designer が、ルールと数値をすべて決めた（`design/first-playable.md`、D-001）。
   - 決めたのは、光の向き（左・上・右）、光る行（灯台の行だけ）、照らされた船の動き（光に沿って灯台から離れる向きに滑る）、難破したら即負け、10 ターンの上限である。
   - あわせて、受け入れ基準 AC-1〜AC-15 と、3 つの夜を用意した。夜はそれぞれ別のことを教える構成である（第 1 夜は船が光に沿って滑ること、第 2 夜は両側から来る船、第 3 夜は 1 隻を暗いままにすること）。
3. **Build（3 回）:**
   - 1 回目: エンジニアは、ゲーム本体、`play.py`、試験、説明書をゼロから書いた。そのうえで、仕様の中の食い違い（第 3 夜の最初の画面に光を描くか）を見つけ、推測せずに `question` で返した。ランナーの試験は exit 1 だった。
   - Design: Designer が食い違いを解いた。
   - 2 回目: ランナーの試験は exit 1 だった。
   - 3 回目: 試験だけを直して exit 0 になった。
4. **Verify:** QA は、AC-1〜AC-15 をすべて合格とした。欠陥は見つからなかった。
5. **Play:** Playtester は説明書とビルドだけを使って、第 1〜3 夜をすべて勝った。負ける手順も試した。報告は具体的だった。たとえば「何もしないと岩に当たるので、船を左端の港まで横に送るのが課題」。
6. **Review:**
   - 達成と判断した。3 つの柱は、定性的には成り立っていると見た。
   - 実時間の長さは、スクリプトでは測れないので未確認とした。
7. **Close:**
   - `project.md` の `## Current state` を、「コンセプトだけ」から、ビルドの中身、遊び方、試験の数、既知の問題、次の Goal の案に書き換えた。ほかの節は変わっていない。
   - Outcome には、次の Goal の案を 5 つ挙げた（夜の奥行き、最後の画面が二重に出ること、未観察の経路、夜の途中で現れる船、説明書の補足）。
