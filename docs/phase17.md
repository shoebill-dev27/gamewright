## 3. コンセプト：Ember Hollow（燠の洞）

- **どんなゲームか:** ターン制の短いローグライク。
  - 燠（おき）を 1 つ持って、洞窟を 5 階まで下りる。
  - 燠は、明かりであり、時間でもある。光の届く範囲がそのまま見える範囲で、毎ターン少しずつ弱まる。各階の篝火（かがりび）でだけ、また強くなる。
  - 洞の生き物は闇に棲み、光に反応する。5 階にいる、洞を暗く保つ生き物を倒せば勝ち。死ぬか、燠が消えれば負け。
- **柱:**
  1. 毎ターンが判断。移動、待機、戦闘、アイテムの使用。次のターンに傷を負わせうる脅威は、すべて先に見えて読める。
  2. 光が資源。遠くまで見えることと、時間が残ることは同じ。燠をどう使うかが、ランの中心の取引。
  3. ランは短く、毎回違う。1 ランは 15〜30 分。階は種（seed）から作られ、種が違えば別のラン、同じ種なら同じラン。
- **制約:**
  - Node.js 20 とブラウザで動く JavaScript。依存なし、ネットワークは使わない。ルールのコードは、2 つの遊び方で共有する。
  - **人のためには、ブラウザのページ。** `repo/index.html` は、サーバーなしでファイルから直接開け、キーボードかマウスで遊べる。階を格子で描く。
  - **チームのためには、入力のスクリプト。** `run_play`（`node play.js {script}`）、`run_trace`、`run_tests`（`node --test`）。スクリプトの書式（種の選び方を含む）はビルドが決め、`repo/manual.md` に書く。
  - 決定的。同じ種と同じ操作なら、いつも同じラン。
- 敵の種類、アイテム、階の大きさ、数値は、すべて Studio が決める。

## 4. 外部の判定（実行前に決める。packet には入れない）

Close の後に、私が判定する。スクリプトでの判定は、`repo/manual.md` と、`project.md` に宣言されたコマンドだけを使う。

| 基準 | 内容 |
|---|---|
| V1 スクリプトで遊べる | 説明書の書式で書いたスクリプトで、ある種のランを `run_play` で進められる |

### 6.2 経過

1. **Design:** Designer が、仕様と受け入れ基準 30 項目を書いた。
   - 敵は 3 種類（蛾、影、猟犬）と、ボスの Gloom。
   - アイテムは 2 種類（軟膏、油）。各階に篝火が 2 つ。
2. **Plan:** Technical Director が、ルールのコードを、ページとテキスト版で共有する作り（D-001）に決めた。ファイルから直接開けるように、モジュールではなく通常のスクリプトで書く。
3. **Build と Design を並行して実施（各 3 回）:**
   - エンジニアがゼロから作り、試験は毎回通った（ランナーの試験は exit 0）。
   - その間、Designer は 2 回呼ばれ、仕様の問いに答えた。脅威の印に加えて「踏むと傷を負うマス」の印をつけること（D-002）と、篝火の閃光で生き物が動けなくなる長さである。
4. **Verify:** QA は実行の要求を 1 回しか使わず、`partial` で返した。試験の結果を一部しか見ていない。
5. **Play:** Playtester は、種 42 の 1 階を 16 ターンだけ遊んだ。
6. **Review と Close:**
   - Director は、ここで予算を使い切ったので、工程は足せないと判断した。
   - 未確認の点を明記して「一部達成」とした。Route は Goal を閉じた。

### 6.5 見つかったこと

1. **大きなゲームも、コンセプトから一通り作れた。** 階の生成、光、敵 3 種とボス、アイテム、ページとテキスト版の共有、試験 49 件。外部の判定では、5 階まで勝ち抜けるランがあることまで確かめられた。
2. **予算の目安は、Goal の大きさを数えていない。**
   - Intake の予算 19 は、「工程ごとに 2、戻り 1 回に 4、Intake に 1」の式どおりだった（工程 7 つ）。
   - しかし大きな Build は、Design との行き来で 6 オペレーションを使った。そのしわ寄せで、QA は 1 回の実行、Play は 16 ターンだけになった。
   - Studio は、予算を守るために検証を浅くした。そのことを正直に書いて「一部達成」で閉じた。
   - 小さな Goal（Phase 14〜16）では問題にならなかったが、大きな Goal では、予算が検証の深さを削る。
3. **Studio は、自分が確かめていないことを、確かめたとは言わなかった。**
   - Review は、ページ、通しのプレイ、柱 2・3 を「未確認」とし、Owner に確認を頼んだ。
   - 実際には、ビルドは私の外部の判定でよく動いていた。Studio の自己評価は、控えめで正確だった。
4. **Studio は、画面を見られない UI を、ルールと描画を分けることで扱った。**
   - ページはルールを呼ぶだけで、ルールのコードを持たない（D-001）。ルールはテキスト版と試験で確かめられる。
   - ページそのものの確認は、人に任せた。
5. **予算を超えそうなとき、Owner に費用を聞かずに閉じた。** 予算の規則では、費用の確認（Owner の工程）も選べた。Director は閉じることを選び、続きを次の Goal の提案にした。
