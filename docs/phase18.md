# Phase 18 設計：Studio に目を持たせ、Ember Hollow に絵をつける

状態: **設計**（2026-10-26。Owner の感想「それぞれに絵がつけば風来のシレンみたいな感じのゲームになるね」と、計画への「OK」により進める）

## 1. 課題

- Phase 17 の Ember Hollow について、Owner は「絵がつけばジャンルのゲームになる」と評価した。次の Goal は、絵をつけることである。
- しかし、Studio は画像を見られない。
  - executor が受け取るのは文字の packet だけで、実行の結果も文字である。
  - Phase 17 では、ページを誰も見ていないので、Review は「一部達成」にとどまった。Art Director の工程も、見る手段がないので省かれた。
  - このままでは、絵の出来や見分けやすさを、Studio 自身が確かめられない。
- 予備の確認として、次の 2 つができることを確かめた。
  - サンドボックスの中（ネットワークなし、見えるのはビルドだけ）で、ヘッドレスのブラウザがページを開き、キーを押して、画面を撮れる。
  - ツールを持たない isolated な executor に画像を渡すと、画面の内容を正しく読み取れる。

## 2. 方針

1. **画面を撮る実行（`shot`）をランナーに足す。** プロジェクトが `project.md` に `page:`（ビルドの中のページ）を書いていて、手元にブラウザがあれば、Step は `@run/shot` で画面を撮れる。
2. **撮った画像を、次の executor にそのまま渡す。** 文字の packet に画像を添える。
3. **画面を見る Role に `shot` を許す。** Art Director、Playtester、QA、Designer、Director。
4. Ember Hollow に、Goal「それぞれに絵をつけてほしい」を渡す。

## 3. 設計

### 3.1 画面を撮る実行

- `project.md` の frontmatter に `page: <ビルドの中のページ>` を書く（例: `page: index.html`）。
- ランナーは、`page:` があって、ブラウザ（Chromium）とその操作のライブラリ（Playwright）が手元にあれば、実行の候補に `shot` を加える。なければ候補に出さない。
- `@run/shot` の中身（スクリプト）の書式:
  - 1 行目に `page <ページ>[#<フラグメント>]` を書ける。書かなければ `page:` のページを開く。フラグメントで、たとえば種を指定できる。
  - そのあとは、押すキーの名前を空白か改行で区切って並べる（`ArrowLeft`、`a`、`Space` など）。
  - `shot` と書いた時点で画面を撮る。最後の画面は、いつも撮る。1 回の実行で最大 4 枚。
- 実行はサンドボックスの中で行う。
  - 見えるのは、システムのプログラム（読み取りのみ）、ビルドの写し、ブラウザとライブラリ（読み取りのみ）だけ。ネットワークはない。
  - ブラウザ自身のサンドボックスは切る。外側の bubblewrap が隔離するためである。
  - 結果の文字には、撮った枚数と、ページのコンソールのエラーを入れる。

### 3.2 画像を executor に渡す

- 撮った画像は、記録に PNG で残し、次の executor の packet に添える。
  - 実行結果の文字には、「画像 1（`@run/shot/<label>` の 1 枚目）」と書く。
  - 添えるのは最新の実行の画像だけで、最大 4 枚。
- Claude の executor には、文字と画像を 1 つのメッセージで渡す。ツールは今までどおり持たせない。
- Codex の executor には、画像を渡す手段を用意しない。画像のある packet は、実行時のエラーにする（Codex は、いまは使わない）。

## 4. 退けた案、見送った案

| 案 | 理由 |
|---|---|
| 画面を文字（ASCII）にして渡す | 絵の良し悪しは文字では分からない。今回の Goal の要点そのものである |
| ブラウザをサンドボックスの外で動かす | ビルドのコード（信頼できない）をホストで動かすことになる。サンドボックスの中で動くことを確かめた |
| 画像を何枚でも渡す | packet が重くなる。1 回の実行で 4 枚、最新の実行の分だけにする |
| 画像ファイル（PNG など）を executor に書かせる | executor が書けるのは文字のファイルだけである。絵は、コード（canvas）か SVG で描くことになる。それで足りるかを、この Phase で見る |

## 5. 前提とリスク

- ブラウザとライブラリは、手元の Playwright のキャッシュから見つける。ない環境では `shot` が候補に出ないだけで、ほかは今までどおり動く。
- 画像は 1 枚あたり数万トークンにあたる。画面を撮る工程が増えると、出力ではなく入力のコストが増える。
- Studio が描く絵は、コードで描く図形になる。手描きの絵ほどの質は期待しない。見分けやすさと雰囲気を見る。
