# Phase 3 設計案：Owner 判断が必要になるまで連続実行する

状態: **実装・検証済み**（設計は 2026-10-11 に承認。§1〜8 は承認時の設計、§9 以降が結果）

正典は `docs/spec/initial-spec.md` と `studio/`。Phase 2 で作った「1 オペレーション = 1 fresh executor」の仕組みは変えず、その上に仕様 §18 の第 2 段階を載せる。

```text
Goal
↓
Studio が複数工程を自動実行
↓
Owner 判断が必要な時だけ停止
```

## 1. 課題

1. **人間が毎回 `next` を押している。** Phase 2 では Step 1 回と Route 1 回で止まる。
   - Owner が本来判断すべきでない進行操作まで、人間が担っている。
   - 戦闘改善 Goal では 52 回だった。
2. **Route は最新の成果物 1 件しか見られない。** そのため次のことが起きた。
   - 後回しにした並列ステップ（2b）の Handoff を組めない。
   - Codex の Route は、原文を読めないことを理由に止まった。
   - 1 回の Route で Handoff を 1 件しか書けないので、並列ステップを順番に処理するしかない。
3. **ループ上限は Route（LLM）の判断にしか頼っていない。** 連続実行では、Route が規則を見落としたときに止める仕組みが要る。Codex では、同じ不足を理由とした差し戻しが 3 回続いた。

## 2. 前提

- 連続実行は**上限つき**であり、無限ループにはしない。上限に達したら止まり、人間が再開を決める。
- **次工程の判断は Route（LLM）のまま**。ランナーが行うのは、規則の検証と停止条件の判定だけ。
- Phase 2 の `next` / `decide` と手動運用はそのまま使える。
- dry-run の Owner は、これまでどおり私が模擬する。どの回答が模擬かは記録に残す。

## 3. 設計

### 3.1 `run` コマンド（連続実行）

```bash
python3 scripts/studio_run.py run <ws> [--max-ops 25]
```

Goal が active な間、次を繰り返す。各回とも別々の fresh executor で実行する。

1. open なステップがあれば実行する。並列ステップ（2a、2b）が複数 open なら、1 つずつ実行する。
2. 必要なら Simulator を実行する。
3. Route を 1 回実行する。

**停止条件。** 次のどれかで止まり、理由を表示して記録に残す。

| 停止理由 | 人間がすること |
|---|---|
| Goal が done / abandoned | Outcome を読む |
| **Owner escalation**（blocked-on-owner） | `decide` で回答してから `run` |
| 検証による拒否が再試行でも直らない | 内容を確認する。状態は書き換わらないので、`run` で再開できる |
| 実行時エラー（利用上限など） | 解除後に `run` |
| **オペレーション上限**（既定 25） | 続けるなら `run` |
| **進展なしの検知**（3.3） | 確認してから `run`（その回の `run` 内でのカウント） |

### 3.2 Route の入力と出力の拡張

**(a) 新しい成果物をすべて渡す。** Route の packet には、前回の Route / Intake / Resume より後にできた成果物をすべて入れる。

- 並列ステップの合流に必要になる。
- 「前回どこまで見たか」は Route の記録に `seen_through_seq` として残し、決定的に計算する。

**(b) 追加資料の要求（1 回まで）。** Route は、出力の代わりに `@need` ブロックで追加で読みたいファイルを要求できる。

- 要求できる範囲: この Goal の成果物とプロジェクトのファイルのみ、最大 8 件。
- ランナーはそれを packet に加えて、**新しい executor で 1 回だけ**再実行する。
- 要求の内容と、2 回目の packet も記録に残す。
- records や studio の外のファイル、9 件以上の要求は拒否する。
- 既定の packet は小さいまま保ち、本当に必要なときだけ原文を読ませるための仕組み。

**(c) 1 回の Route で複数の Handoff を書けるようにする。** 連番で最大 3 件まで。後回しにしていた並列ステップを、その場で開けるようにする。

### 3.3 進展なしの検知（機械的な安全網）

`run` は次のどちらかの状態になったら止まり、人間に判断を回す。orchestration のループ上限が守られなかったときの保険であり、Route の判断を置き換えるものではない。

- 同じ Role が `question` を連続 2 回返したのに、その Role が 3 回目に開かれた。Codex で実際に起きたパターン。
- この `run` の中で、同じ Role が 4 回以上開かれた。

### 3.4 Owner への返し方

`run` が止まるたびに、次の要約を表示し、記録にも残す。

- 実行したオペレーション数と停止理由
- Owner が読むべきファイル（Escalation か Outcome）
- 次に実行するコマンド

### 3.5 ツール中立の仕様（`studio/`）

- **`execution.md`:** 「連続実行」の節を追加する。停止条件、上限、進展なしの検知、追加資料の要求を、ツール名を含めずに書く。
- **`orchestration.md`:** 次の 2 点を追記する。手動手順はそのまま。
  - Route は並列ステップの Handoff をまとめて書ける。
  - Route は追加資料を要求できる。

## 4. トレードオフ

| 選択 | 採った案 | 退けた案と理由 |
|---|---|---|
| Route に原文をどう渡すか | 必要な時だけ要求させる（1 回まで） | 毎回 studio 宛ての全成果物を入れる案：戦闘改善 Goal では 100 KB を超え、高コストになる |
| ループ対策 | Route の規則判断に加え、機械的な安全網 | 安全網なし：Codex の実例のように、規則を見落とすと上限まで空回りする |
| 上限の単位 | オペレーション数 | 金額や時間：サブスク利用では金額が実額でなく、時間はモデルによって大きく変わる |
| 並列ステップ | 1 つずつ順に実行し、Route は 1 回 | 同時実行：利用上限と記録の順序が複雑になる。今は不要 |

## 5. リスク

- **利用枠の消費。** 人間の確認なしに進むので、1 回の `run` で多くの executor を使う。上限 25 と進展なしの検知で抑える。
- **判断の質のばらつき。** 連続実行では、人間が途中で気づく機会が減る。Owner escalation、検証、記録は今までどおり働く。
- **`@need` の濫用。** 件数の上限、1 回きりの制限、範囲の制限で抑える。
- **fixture の不備がもとで、長い空回りが起きる**（Phase 2 の #6 の例）。進展なしの検知で止める。

## 8. 検証計画

**決定的テスト（fake runtime）:**

- `run` が次の各条件で正しく止まり、それ以上の executor を起動しないこと:
  - escalation
  - done
  - 上限
  - 拒否
  - 実行時エラー
  - 進展なし
- 並列ステップを両方実行してから Route を 1 回実行し、その packet に両方の成果物が入ること。
- `@need`:
  - 要求したファイルだけが 2 回目の packet に加わること。
  - 範囲外や 9 件以上の要求は拒否すること。
  - 2 ラウンド目はないこと。
- 複数 Handoff の Route の検証。
- Phase 2 の隔離テストがすべて通ること。

**実行（Claude、Sonnet）:**

1. バグ Goal を fixture から **`run` 1 回だけで**完走させる（途中で人間が入らない）。
2. 戦闘改善 Goal を `run` で実行する。止まるたびに Owner（模擬）が判断し、`run` で再開して完走させる。オペレーション数を Phase 2（52）と比べる。
3. `lantern-depths-escalation` の fixture で、`run` が即座に停止し、`decide` のあと `run` で進むことを確認する。

**Codex:** 引き続き保留。利用上限が戻ったら、Phase 2 の残り 2 オペレーションを `run --runtime codex` で実行する。

## 9. 結論

Owner 判断が必要になるまで自動で進む `run` は機能した。

- **バグ Goal は `run` 1 回で完走した。** 7 オペレーションで、途中で人間は入っていない（Phase 2 の `next` 方式では 15 オペレーション）。
- **戦闘改善 Goal も完走した。** 人間の起動回数は、Phase 2 の約 26 回の `next` から、9 回の `run` と 3 回の `decide` に減った。
  - Owner 判断が本当に必要だった停止は 2 回で、どちらも根拠つきの選択肢と推奨を返した。
  - 残りの停止は、ランナーの不具合 4 件（その場で修正）、executor の規則違反 1 件、利用上限 1 件。
- Phase 3 の仕組みを実際の実行ですべて確認した。並列ステップと 1 回の Route による合流、追加資料の要求（`@need`）、escalation での即時停止、`decide` のあとの再開、上限による停止。
- **オペレーション数は減らなかった。** 戦闘改善 Goal は 67 回で、Phase 2 の 52 回より多い。主な理由は 2 つ:
  - 並列化で同時に進む作業が増えた（10 回）
  - 拒否と再試行（18 回）
  - Phase 3 が減らしたのは「人間の介入」であり、「工程の数」ではない。

## 12. 判明した問題と対処

| # | 現象 | 対処 |
|---|---|---|
| 1 | 「open にできるのは 1 グループだけ」という検査が、後回しにしていた 2b と新しい 4a / 4b の同時オープンを拒否した | 検査を撤廃した。同時に open なステップは並列とみなし、番号は自由にした（orchestration も修正） |
| 2 | Handoff 列に注記が付いていた（`[12-…](…) (earlier: …)`） | 最初の `NN-*.md` を読むようにした |
| 3 | Route が失敗したあとに `run` すると、Step を再実行してしまう | 未 Route の成果物があれば、先に Route するようにした |
| 4 | 行番号のプライム（`4a′`、`4a″`）が読めず、QA のステップが実行されなかった | 行番号の後ろに任意の文字を許した |
| 5 | QA が古い `sim/build-0.4.md` で検証し、3 回差し戻した。Route はファイル名だけを見て、どれが最新か分からなかった。Owner escalation になった（入力の不足として妥当） | dry-run harness が `current_build` を packet のヘッダに明示するようにした |
| 6 | `@need` をファイルブロックで包まずに書いた | 書式を明示し、包んでいない形も受け付けるようにした |
| 7 | goal.md が肥大化した（Route ごとに全文を書き直すので、出力が 2 万トークンを超えた） | Route changes を 1〜2 行にする規則を追加した。§13 の 1 も参照 |
| 8 | Route が Load にファイル名だけ（`goals/…` なし）を書いた | 拒否メッセージで正しいパスを示すようにした（再試行で直る） |
| 9 | （Codex）Route が「TD に Escalation を作らせる」と決めたのに、Escalation がまだないうちに Goal を `blocked-on-owner` にした。`run` は止まったが、Owner が読むものがなかった | `blocked-on-owner` には open な Escalation が必要という検証を追加した（ブリーフの作成中は active のまま、作成する Role のステップを open にする）。受理済みの誤った Route をやり直すために `route --since N` を追加した。修正後、同じ誤りは 1 回目で拒否され、再試行で正しい状態になった |

確認できた良い挙動:

- ポリシーは連続実行中も働いた。Route が Playtester に設計書や Designer の Handoff を渡そうとした 2 回は、どちらも機械的に拒否された。
- 停止後の要約（読むべきファイル、次のコマンド）は毎回正しかった。
