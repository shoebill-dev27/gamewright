# Phase 4：工程表（goal.md）の構造の見直し

状態: **完了**（2026-10-12 承認、2026-10-13 実装・実地検証）。設計は §1〜§6、結果は §7。

## 1. 課題（実測：`examples/runs/p3-combat-run`）

1. **Route の出力が工程の進行とともに増える。** Route は毎回 goal.md を全文書き直す。
   - goal.md は 54 KB まで膨らんだ。主因は Route changes の段落が毎回追記されていくこと。
   - 1 回の Route の出力は通常 6,000〜10,000 トークンで、最大 27,000 トークン。
   - Goal が長いほど、1 回あたりのコストも失敗の可能性も上がる。
2. **履歴が消える。** Phase 3 で「Route changes を短く」という規則を入れたあと、Route は古い履歴を自分で削って短くするようになった。
   - 最終的な goal.md の Route changes は 913 バイトしか残っていない。
   - 経路変更の理由は、run の記録（record）を掘らないと追えない。
3. **表のセルが長い。** 状態欄に 300 字の説明が入るなど、本来は Handoff に書くべき内容が表に入り込んでいる。
4. **書き換えの規則がない。** Route が Owner の依頼文や解釈を書き換えても、検証で止まらない（実例はないが防いでいない）。

## 2. 方針

**goal.md は「今の状態」だけを持つ。履歴は、ランナーが書く追記専用のログに移す。**

Route が書く内容と書き方はほぼ今のままにし、LLM に新しい書式を覚えさせない。

## 3. 設計

### 3.1 追記専用ログ `goals/<goal>/log.md`（ランナーだけが書く）

- Studio オペレーション（Intake / Route / Resume）が goal.md を書くたびに、ランナーが log.md の末尾に 1 件を足す。
- 各件の中身:
  - 記録番号と日付
  - そのオペレーションの `## Route changes`
  - 状態と、open になったステップ
- Step や Route は log.md を書けない（書き込みリストに入れない）。そのため履歴は消えないし、改ざんもされない。
- 手動運用では、Route を行う人や実行者が同じ形式で追記する（orchestration に明記する）。

### 3.2 goal.md の `## Route changes` は「最新の変更だけ」

- 直前の Route が何を変えたかを 1〜3 行で書く。毎回置き換えてよい。
- 全履歴は log.md にある。
- 見出しは残すので、Phase 1 の成果物とテストはそのまま通る。

### 3.3 Route の packet に「最近の履歴」を入れる

- log.md の直近 5 件を `@log-recent` として渡す。ループに気づくといった判断に必要な文脈は、ここで保てる。
- それより古い履歴が必要なら、Phase 3 の `@need` で `goals/<goal>/log.md` を要求できる。

### 3.4 検証の追加（機械的な歯止め）

| 規則 | 目的 |
|---|---|
| `## Route changes` は 600 字以内 | 履歴が goal.md に溜まるのを防ぐ |
| 表の Stage 欄・Status 欄は各 80 字以内 | 詳細は Handoff に書かせる |
| goal.md 全体は 20 KB 以内（Outcome を除く） | 最後の安全網 |
| Route は Owner request を変更できない。Interpretation は Resume だけが変更できる | Goal の再解釈は Owner の判断事項（仕様 §5）。それを機械的に守る |
| `## Unknowns` は 3,000 字以内（実地検証中に追加。§7.3） | 履歴が Unknowns に移って溜まるのを防ぐ |

違反した場合は、Phase 2 以来の仕組みどおり拒否する。新しい executor での 1 回の再試行で、エラーメッセージが直し方を伝える。

### 3.5 退けた案

| 案 | 理由 |
|---|---|
| Route が表の差分だけを独自書式で出し、ランナーが適用する | 出力は最小になる（約 300 B）。ただし LLM に新しい書式を覚えさせることになり、書式ミスによる再試行が増える。手動運用との両立も難しい。本案で増加が止まらなければ、次の段階として検討する |
| 完了した行を表から自動で退避する | 表の 1 行は約 120 B と小さい（31 行で約 3.7 KB）。効果が小さいので見送る |

## 4. 期待効果

長い Goal でも goal.md は約 7 KB（約 2,000〜3,000 トークン）にとどまり、履歴の長さに比例して増えなくなる。内訳の見込み:

- 依頼文・解釈・Unknowns: 約 2 KB
- 表: 約 4 KB
- 最新の変更と次の手順: 1 KB 未満

Route の出力は「goal.md と新しい Handoff」でほぼ一定になる。

### 7.3 検証中に見つけて直したこと

1. **上限の数値が Route に見えていなかった**（003-route の 1 回目、Route changes が 629 字）。600 字と 80 字は検証にしかなかったため、テンプレートと orchestration に明記した。以後、上限による拒否は起きていない。
2. **Role 欄に注記が入る**（003-route の 2 回目、`qa (∥ art-director)`。Phase 3 でも出ていた）。エラーメッセージで直し方（並列ステップは別の行にする）を示すようにし、テンプレートにも書いた。
3. **手作業で進めていた Goal の最初の Route**: Studio オペレーションの記録がないと、Route には最後の成果物 1 件しか見えず、並列ステップの片方を見落としていた。さらに、Route が拒否されたあとの `run` が、同じステップをもう一度実行していた。記録がない場合は「goal.md にまだ名前が出ていない成果物」を未処理とみなすようにした（`unseen()`）。Route と `run` の両方がこれを使う。
4. **executor を起動できない場合**（014-route）: Route の起動が Claude CLI の自動更新と重なり、コマンドが一瞬存在しなかった。ランナーはこの例外を処理できず、run の要約記録が残らなかった。いまは実行時エラーとして記録して止まる。なお、014-route の記録は修正前のもので、packet だけが残り record.json はない。
5. **履歴が Unknowns に移った**: Route changes が短くなると、Route は各工程の経緯（「…さらに…その後…」）を Unknowns に書き足すようになった（2.0 KB から 5.4 KB）。次の 2 つで対処した。
   - テンプレートと orchestration に「Unknowns は今の状態であり、経緯ではない」と明記した。
   - 3,000 字の上限を追加した。これまでの Intake が書いた Unknowns は最大でも 2,043 字なので、余裕がある。
   - 指示が届いた最初の Route（038）は、Unknowns を 2.5 KB に縮めた。上限は次の run から有効になったが、実地では一度も触れていない。

### 7.4 残る制約

- 表の行は工程ごとに増える（1 行 約 100 B。27 行で 2.6 KB）。§3.5 のとおり退避は見送った。長い Goal でも 20 KB の安全網には遠い。
- Handoff 欄の注記（例:「(result: 12)」）には上限がない。表の増え方への影響は小さい。
- Unknowns の上限は、指示の追加と同時に入れた。そのため、上限がなくても指示だけで十分だったかは区別できない（038 では指示だけで縮んだ）。
- G-001 の Outcome の判定は、シミュレーション上の根拠に基づく（Phase 1〜3 と同じ循環性）。
