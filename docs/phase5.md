# Phase 5：実際に動くビルドで QA と Playtest を回す

状態: **完了**（2026-10-13 承認・実装・実地検証）。設計は §1〜§8、結果は §9。

## 1. 課題

Phase 1〜4 では、ビルドを文章で模擬してきた（dry-run）。そのため検証が循環している。

- **観察しているのが実装の意図になっている。** Build の後、シミュレーターが「エンジニアが書いた変更内容」からビルドの説明文を書き直す。QA と Playtester はその説明文を読む。つまり、実際の挙動ではなく、実装者の意図を観察している。
- **数値の基準を判定できない。** Phase 3 の戦闘 Goal では「未判定」のまま Review に進んだ（D-010）。Phase 4 の G-001 の Outcome も「シミュレーション上の根拠」止まりだった。
- **分かっていないこと:** Studio の手順が正しく回ることは確かめた。しかし Studio の仕事で、ゲームが本当に直るかは確かめていない。

## 2. 方針

**executor には今までどおりツールを持たせない。** そのうえで、プロジェクトが宣言したコマンドだけをランナーがサンドボックスで実行し、その結果を新しい executor に渡す。

- 仕組みは Phase 3 の追加資料要求（`@need`）と同じで、資料の代わりに実行結果を足す。
- Phase 2 の保証はすべて保つ。1 オペレーションに 1 つの新しい executor を使い、packet がすべての入力で、成果物だけが引き継がれる。
- コードの変更は、プロジェクトのリポジトリにある実ファイルへの変更になる。

## 3. 設計

### 3.1 実際に動くサンプルゲーム `examples/fixtures/lantern-depths-real/`

- Project Context は lantern-depths と同じにする（vision、`design/combat.md`、D-001）。
- `repo/` に小さなゲームを置く。
  - 画面のない Python ゲームで、標準ライブラリだけを使う。約 300 行。
  - 固定ステップのシミュレーションで、`--fps 30|60` を指定できる。プロジェクトの制約「30 と 60 FPS の両方で正しく動く」を、実際に確かめられる。
  - 中身: 攻撃、ダッシュ、被弾、無敵時間、Grub と Spitter、部屋。
  - 入力スクリプト（例: `0.50 dash right`）を受け取り、結果を 2 種類の表示で出す。
    - `player`: プレイヤーに見えるものだけ。文字の画面、ハートの数、「被弾した」など。
    - `trace`: 内部の状態とイベント。無敵フラグやタイマーなど。
- **元の不具合をそのまま入れておく。** 無敵フラグは 1 つしかなく、タイマーが 2 本ある。被弾直後にダッシュすると、被弾側のタイマーがダッシュの途中でフラグを切ってしまう。
- `repo/tests/` には unittest を置く。無敵時間のテストは入れない。
- コードにカナリア文字列を入れる。Playtester に届かないことを、テストで確かめるためである。

### 3.2 プロジェクトが実行コマンドを宣言する（`project.md` の frontmatter）

```text
build: repo
run_tests: python3 -m unittest discover -s tests
run_play: python3 play.py --view player --script {script}
run_trace: python3 play.py --view trace --script {script}
```

- コマンドは `repo/` の中で実行する。
- `{script}` は、executor が書いた入力スクリプトのファイル名に置き換える。
- `build:` がないプロジェクトは、従来どおり dry-run で動く（tidepool-garden など）。

### 3.3 実行要求 `@run`（Step のみ、最大 3 回）

**流れ**

1. Step は最終的な成果物の代わりに、次の 1 つ以上のブロックで答えてよい。
   - `@run <名前>` のブロック（中身は入力スクリプト。tests の場合は空）
   - そのロールが書いてよいリポジトリのファイルなら、変更案のブロックも一緒に出せる
2. ランナーは `repo/` を一時ディレクトリにコピーし、変更案を当ててから、各コマンドをサンドボックスで実行する。
3. 新しい executor を起動する。渡すのは、同じ packet に次の 2 つを足したものである。
   - 実行結果（コマンド、入力、終了コード、出力）
   - 前の executor が出した変更案とスクリプト
4. 実行要求は 1 Step あたり 3 回までで、最後は通常の成果物で答える。すべて記録に残す。

**ロールごとに実行できるコマンド**（frontmatter の新しいキー `runs:`。既存のポリシーと同じ方法で強制する）

| ロール | runs |
|---|---|
| gameplay-engineer | tests, trace |
| qa | tests, play, trace |
| playtester | play（プレイヤー表示だけ） |
| その他、および Route / Intake / Resume | なし |

- エンジニアは自分の変更をテストできる。その結果は Sender assessment に書くので、QA には届かない。QA は自分で実行し直して、独立に検証する。
- Playtester は、コードも内部状態も見ずにプレイの結果だけを受け取る。
- エンジニアが書いてよいファイルは `writes: repo/**` で、既存の仕組みで検証する。

### 3.4 サンドボックス（bubblewrap、使えないときは実行しない）

- 見せる範囲:
  - `/usr` は読み取り専用。
  - 一時ディレクトリ（リポジトリのコピー）は `/work` として読み書き可。
  - それ以外は見えない。`/home`、`/mnt/c`、`/etc` も含む。
- ネットワークは遮断する（`--unshare-all`）。環境変数は空にする。
- 1 コマンドあたり 30 秒で打ち切り、出力は 20 KB で切る。
- bubblewrap がなければ実行時エラーとして止まる。サンドボックスなしでの実行には切り替えない。
- この環境で確認したこと:
  - ネットワークは遮断された。
  - `/work` 以外への書き込みは、ホストに残らない。
  - `/home`、`/mnt/c`、`/etc/passwd`、`~/.ssh` は見えない。

### 3.5 dry-run の仕組みとの関係

- `build:` があるプロジェクトでは、シミュレーターを使わない。
- packet ヘッダの `current_build` には、`repo/` のファイル群の短いハッシュを入れる。
- Studio 側の文書（Role、Skill、orchestration）は、ほとんど変えない。Skill はすでに「テストを実行する」「ビルドを実行する」と、ツールに依存しない言い方で書いてある。
- 主に変えるのは次の 2 つである。
  - `execution.md`: 実行要求とサンドボックスの保証を追加する。
  - Role の frontmatter: `runs:` を追加する。

## 4. 退けた案

| 案 | 理由 |
|---|---|
| executor にシェルなどのツールを持たせる | 自然で簡単。ただし Phase 2 の「packet がすべての入力」が崩れる。読めるファイルを機械的に制限できなくなる |
| 決まったシナリオをランナーが自動実行するだけにする | 単純。ただし QA が再現手順を組めず、Playtester が遊び方を選べない |
| 本物のエンジン（Godot、Unity、ブラウザ） | 現実的。ただし依存が重く、画面なしでの実行も複雑になる。コマンドを宣言する方式はエンジンに依存しないので、後から差し替えられる |
| Docker | 動作が重く、デーモンが要る。bubblewrap は軽く、この環境ですでに使える |

## 5. 前提とリスク

**前提**

- Sonnet が、約 300 行のコードのファイル全体を正しく書き直せる。出力の形式は、ファイル全体を出す今の方式のままにする。
- bubblewrap はこの環境で使える（確認済み）。

**リスク**

- **ファイル全体の書き出し:** 小さいファイルなら問題ない。大きなプロジェクトでは差分の形式が必要になる（後の課題）。
- **コスト:** 実行要求の 1 回ごとに executor が 1 つ増え、1 Step あたり最大 3 つ増える。
- **入力スクリプトの書き間違い:** エラーの出力が返り、実行要求を 1 回使う。
- **LLM が書いたコードを実行すること:** サンドボックスで閉じ込め、使えないときは実行しない（§3.4）。

## 6. 範囲外（次の候補）

- 体験の数値（戦闘 Goal の「単調さ」など）をボットのプレイで測ること。Phase 5 は、まずバグ Goal で「実際に直ったか」を確かめるところまでにする。
- 人間によるプレイテスト。
- Codex での実行。

### 9.2 実地検証：`runs/p5-bug-run`（Claude、Sonnet）

バグ Goal（「ダッシュ中なのにダメージを受けることがある。再現できるので直してほしい。」）を、`fixtures/lantern-depths-real` から `intake` と `run` 1 回で完走させた（`done`）。

**経過**

- 7 オペレーション: Intake → QA の Observe → Route → エンジニアの Build → Route → QA の Verify → Route（Close）。
- executor セッションは 12 個で、すべて別。ツール使用は 0 件。
- 実行要求は計 5 回（QA 2 回、エンジニア 1 回、QA 2 回）、実行したコマンドは 21 本。どれも 0.1 秒未満で終わった。
- **QA の Observe**（2 回）: 30 FPS と 60 FPS の trace で再現し、ビルドのテストも実行した。プレイヤー表示でも被弾を確かめた。設計の規則に反することを示して、エンジニアに渡した。
- **エンジニアの Build**（1 回）:
  - 修正とテスト 7 件を提案して実行したところ、自分のテスト 3 件が 30 FPS で失敗した。
  - テストを直して最終版を書いた。最終版のテストは再実行していないが、QA が独立に実行して通った。
  - 修正は根本原因に対するものだった。無敵かどうかを、ダッシュと被弾の両方のタイマーから決める形にした。
- **QA の Verify**（2 回）:
  - テストの再実行を含めて計 13 本を走らせた（テスト 1、trace とプレイ 12）。範囲は 30/60 FPS、すり抜け、上下のダッシュ、先行入力の攻撃、Spitter の弾、部屋 3、被弾タイマーがダッシュ中に切れる場合。
  - 合格と判定した。
- **Outcome**（日本語）: 修正内容、検証の範囲、新しく見つかった論点（ダッシュ直後の猶予）を Owner に示した。

**外部の判定（循環を断つ）**

- Studio のどの packet にも入れていない判定で、最終的な `repo/` を確かめた（`tests/test_phase5.py`）。
  - シナリオは 2 つ: 被弾直後のダッシュと、被弾後の無敵時間中のダッシュ。
  - それぞれを 30 FPS と 60 FPS で実行した。
- 結果は、ダッシュ中の被弾も、被弾から 0.8 秒以内の再被弾もなし。ビルドのテスト 14 件もすべて成功した。
- 同じ判定は、修正前のビルドでは両方の規則違反を検出する。
- **Studio が「直った」と判断した内容は、外から見ても正しかった。**

**独立性**

- QA の packet にエンジニアのソース（`repo/game.py`、実装側のカナリア）は入っていない。Route は QA に、`play.py` とテストだけを渡した。
- エンジニアの自己評価（Sender assessment）も、QA には届いていない。

**コスト**

- packet の大きさ: QA は 22〜61 KB、エンジニアは 38〜57 KB（ソースとテストの全文、実行結果を含む）。
- 出力トークンの最大は、エンジニアの最終回の 11,360。ファイル全体を書き出すため。

### 9.3 検証中に見つけて直したこと

- **Load 一覧は `.md` しか読んでいなかった**（実地検証の 1 回目で発見）。
  - Handoff の Load にある `repo/game.py` などが黙って無視され、エンジニアはソースを受け取れなかった。エンジニアは 2 回とも「ソースが届いていない」と差し戻した。
  - Route は orchestration の規則どおり、同じ入力不足が 2 回続いたので Owner に確認した。選択肢には「実行環境を直す」を挙げていた。Studio は正しく動き、壊れていたのはランナーだった。
  - 修正: ディレクトリを含むパスであれば、どの種類のファイルでも Load として読むようにした（`repo/game.py`、`repo/tests/test_game.py` など）。
  - 回帰テストを追加した。1 回目の記録は今の読み取り方と合わないので、リポジトリには入れず、修正後に Intake からやり直した。

### 9.4 残る制約

- **Playtester の経路は実地では通っていない。** バグ Goal には Play の工程がなかった。プレイヤー表示だけを渡す制限は、決定的テストでのみ確かめた。体験系の Goal は次の候補（§6）で扱う。
- エンジニアは最終版を再実行せずに提出できる。今回は QA の独立した検証が受け皿になった。
- 出力はファイル全体を書く方式のため、ファイルが大きくなるとコストが比例して増える（§5）。
- Load に書けるのは「`.md` のファイル」と「ディレクトリを含むパス」だけ。プロジェクト直下の `.md` 以外のファイルは読めない。
- サンドボックスは bubblewrap を前提にしており、この環境（WSL2 の Ubuntu）でだけ確かめた。
