# Phase 6：体験系の Goal を実際に動くビルドで回す

状態: **実地検証を途中で停止**（2026-10-15 承認・実装、2026-10-16 停止）。設計は §1〜§8、結果は §9。Goal は Close に至らなかった。理由は §9.4。

## 1. 課題

Phase 5 で「バグが本当に直ったか」は外から判定できるようになった。まだ確かめていないのは、Studio のもう半分である体験の評価である。

- **Playtester の経路が実地で通っていない。** プレイヤーに見えるものだけで遊び、体験を報告する流れは、決定的テストでしか確かめていない。
- **体験の数値を判定できない。** Phase 3 の戦闘 Goal は「単調さ」の数値の基準を判定できないまま Review に進んだ（D-010）。
- **体験が本当に良くなったかを外から判定していない。**

### 1.1 準備で分かったこと：Phase 5 のビルドは「単調」ではない

単純な戦い方をするボットと、ダッシュを使うボットを試作し、Phase 5 のビルドで遊ばせた。

| ビルド | その場で斬るボット | ダッシュを使うボット |
|---|---|---|
| Phase 5 のフィクスチャ（不具合あり） | 5 部屋中 3 部屋で倒れる | 同じく 3 部屋で倒れる |
| Phase 5 の修正後（`runs/p5-bug-run`） | 部屋 3 と 5 で倒れ、失ったハートは計 7〜10 | ほぼ無傷（計 0〜1） |

修正後のビルドは、すでにダッシュの腕前が報われる作りになっていた。プロジェクトの説明（「同じやり方で全部屋に勝てる。ダッシュはほとんど要らない」）と、実装の挙動が食い違っている。Phase 5 は不具合だけを扱ったので、このずれは問題にならなかった。

## 2. 方針

1. **出発点のビルドを、説明どおりに単調にする**（新しいフィクスチャ）。
2. **戦闘 Goal**（Phase 3 と同じ依頼文「戦闘が単調なので改善したい」）を、そのビルドで `run` する。Playtester は実際にプレイする。
3. **数値はボットで測る。** ボットには 2 種類を用意する。
   - **Studio が使うボット**: ビルドに含まれ、Designer と QA が基準の設定と検証に使う。
   - **外部の判定用ボット**: 別に実装し、どの packet にも入れない。
4. **判定の基準は実行前に決めて、本書に書いておく**（後から都合よく変えないため）。

### 3.2 Playtester の経路

仕組みは Phase 5 のまま変えない。Playtester は入力スクリプトを書いてプレイし、プレイヤーに見える表示だけを受け取る。最大 3 回まで、結果を見て遊び方を変えられる。

**制約:** 入力は先に決めておく必要があり、敵の動きにその場で反応できない。リプレイを見ながら次の遊び方を決める形に近い。単調さ（「その場で斬っていれば勝てる」）を感じ取るには足りると考えるが、検証で確かめる（§8）。

### 3.3 外部の判定（実行前に決める基準）

`tests/test_phase6.py` に、外部の判定用ボットを 2 つ置く。どの packet にも入れない。

- **単純な戦い方**: 近づき、敵の方を向いて斬る。弾は横に避ける。ダッシュは使わない。
- **腕のある戦い方**: 単純な戦い方に加え、弾、囲まれたとき、急に速く近づく敵（溜め攻撃など）からダッシュで逃げる。

知らない種類の敵は、近づいてくる脅威として扱う。

**成功の基準**（30 FPS と 60 FPS の両方で満たすこと）

| # | 基準 | 意味 |
|---|---|---|
| S1 | 単純な戦い方が、2 部屋以上で「ハートを 2 つ以上失う」か「倒れる」 | 同じやり方で全部屋に勝てる、という単調さがなくなった |
| S2 | 腕のある戦い方は 4 部屋以上を突破し、失うハートの合計が単純な戦い方より 3 以上少ない | 腕前が報われる |
| S3 | ビルドのテストが通る。新しい入力が増えていない（増やすなら、D-001 を置き換える Owner の Decision がある） | 柱 1 と D-001 を守っている |

- 結果は合否にかかわらず報告する。
- 測った値は `measurement.json` として実行記録に残す。テストは、その値が再計算でも同じになることだけを確かめる。そのため、判定が不合格でもテストは赤くならない。
- **限界:** これは「単調さ」を測る 1 つの方法にすぎず、「面白さ」そのものは測れない。

**提案:** 検証の実行中は私が Owner の代わりに答え、Studio の推奨案を採用する。Escalation と回答は記録に残す。

## 4. 退けた案

| 案 | 理由 |
|---|---|
| Phase 5 で修正したビルド（Studio の出力）から始める | 話の流れとしては自然。しかし説明どおりに単調ではなく、バランスを変えると Phase 5 で足されたテストが壊れる |
| 外部の判定に、Studio と同じボットを使う | Studio がそのボットに合わせ込むと、判定の意味がなくなる |
| ボットを Studio に渡さない | Designer と QA が数値の基準を決められず、Phase 3 の「未判定」に戻る |
| Playtester がその場で反応できるようにする（1 フレームずつのやり取り） | executor の数が爆発的に増える。まずは入力を先に決める方式で十分かを確かめる |

## 5. 前提とリスク

- **ボットが「腕前」を正しく表せるとは限らない。** Studio が新しい仕組みを入れると、外部の判定用ボットがそれに対応できず、判定を誤るおそれがある。そのため、結果はコードの差分を読んだうえで解釈する。
- **エンジニアは `repo/bots.py` も書き換えられる。** チームの道具を合わせ込む危険があるが、外部の判定がその歯止めになる。
- **コスト:** Phase 3 の戦闘 Goal は 67 オペレーションかかった。今回は実行要求の分も増え、executor が 60〜100 回ほどになる見込み（サブスクリプションの利用枠を使う）。

### 9.3 外部の判定（§3.3 の基準。実行前に決めたもの）

| | 出発点（ビルド 0.4） | 停止時点 |
|---|---|---|
| 単純な戦い方（30 / 60 FPS） | 5 部屋突破、失ったハート 2 / 1 | 5 部屋突破、失ったハート 0 / 0 |
| 腕のある戦い方（30 / 60 FPS） | 5 部屋突破、失ったハート 3 / 1 | 5 部屋突破、失ったハート 0 / 0 |
| 新しい入力 | なし | なし |

**判定: S1 不合格、S2 不合格、S3 不合格。**

- **S1 と S2:** 単純な戦い方は、以前よりさらに楽に勝てる。腕前も報われない。
  - 案 A で敵は攻撃の前に溜めを見せ、溜め中と噛みつき中は斬れなくなった。人がその場で反応すると「避けて、隙を突く」リズムが生まれるはずの設計である。
  - しかし毎フレーム反応するボットは、敵が溜めに入る前に届いた瞬間から斬り続けるので、溜めを見る前に倒してしまう。
  - 事前に決めた測り方では、**単調さは解消せず、むしろ簡単になった**。
- **S3:** 決められた `run_tests`（ビルドだけのコピーで実行）では、説明書のテスト 2 件がエラーになる。`manual.md` を `repo/` の隣に置けば 73 件すべて通る。ビルドが壊れているのではなく、§9.4 の 2 の問題である。
- **観察者どうしの食い違い:**
  - 外部のボット（毎フレーム反応する）: 無傷で突破する。
  - Playtester（入力を先に決める）: 部屋 1 で倒れる。
  - どちらも人間ではない。人間の手応えはこの中間にあると考えられるが、今回の仕組みでは測れない。

### 9.4 見つかった問題

1. **Playtester が先に進めない（いちばん大きい）。**
   - 入力を先に決めて遊ぶ方式では、溜めに反応できない。
   - 新しい Playtester 4 人が全員部屋 1 で倒れ、Play の証拠が毎回薄かった。そのため Studio は Diagnose と Play をやり直し続けた。
   - 設計時に挙げた制約（§3.2）が、ビルドが反応を求めるようになった途端に致命的になった。
2. **ビルドの外にあるプレイヤー向け文書（`manual.md`）を、誰も書けない。**
   - エンジニアの書き込み範囲は `repo/` だけで、サンドボックスにもビルドしか入らない。
   - その結果、Owner への確認が 6 件出た。エンジニアの書いた説明書のテストも、Studio 内では一度も通らなかった。
   - フィクスチャの作り（説明書をビルドの外に置いた）と、ランナーの仕組みの両方の問題である。
3. **`run` は、Goal を `active` のまま出された Owner への確認に気づかない。**
   - Route が「その間に進める作業」と一緒に Escalation を出すと、Goal は `active` のまま進む。
   - `run` は Goal の状態しか見ないので、確認が未回答のまま進み続けた（62、79）。
4. **ボットの書式が見つけられない。**
   - 書き方は `repo/bots.py` の中にしか書いておらず、エラーメッセージも使い方を示さない。
   - そのため bots の実行 16 回中 10 回が書式エラーだった（フィクスチャの不備）。
5. **コスト。**
   - エンジニアは毎回ファイル全体（`game.py` 800 行、テスト 1,150 行）を書き直し、1 回の出力が約 7.5 万トークンになった。
   - Phase 5 で挙げた「ファイル全体を書く方式」の限界（§5）が、実際の規模で表に出た。
6. **エンジニアの出力が 2 回拒否された。**
   - 1 回目は Handoff の付け忘れ。2 回目は、書けない `manual.md` を実行要求に混ぜた。
   - 拒否そのものは正しい判定だった。ただし後者のエラーメッセージは「最終の答えに書いて」と誤った案内をしていたので、直した（書けないファイルだと伝える）。

**うまく動いたこと**

- **Playtester の経路は実地で通った。**
  - 5 回とも、プレイヤー表示だけで遊び、具体的な体験を報告した。たとえば「避けて隙を突くリズム」「溜め中は斬れない」「向きを変えるには動くしかない」。
  - 隔離の規則（Load、カナリア、実行権限）は破られなかった。
- **QA は実際のビルドで大量に検証した**（play 102、trace 89）。Owner が実行したテストでは失敗が 1 件見つかり、Designer がテストの側を直すと裁定した（D-008、D-009）。
- **Studio は規則どおりに動いた。** 同じ入力不足が 2 回続いたら Owner に上げ、並列に進められる作業は進め、Decision を記録した。

### 9.5 次の候補

| 優先 | 内容 |
|---|---|
| 1 | **Playtester がその場で反応できるようにする。** 「画面にこれが見えたらこうする」という、プレイヤーの言葉で書いた反応の規則を、play コマンドがフレームごとに実行する。プレイヤーに見えるものだけを条件にできる |
| 2 | **プレイヤー向け文書を、ビルドと一緒に扱う。** たとえば `manual.md` をビルドの中に置く。またはプロジェクトが文書を宣言し、サンドボックスに含めて、担当の Role が書けるようにする |
| 3 | **未回答の Owner への確認を、`run` が報告し、それしか残っていなければ止まる** |
| 4 | 大きなファイルの差分形式での出力 |
| 5 | ボットの書式を見つけやすくする（使い方の表示、プロジェクトの説明） |
