# Phase 7：Playtester がその場で反応できるようにし、戦闘 Goal をやり直す

状態: **完了**（2026-10-16 承認・実装・実地検証）。設計は §1〜§7、結果は §8。戦闘 Goal は、外部の判定の基準 S1〜S3 をすべて満たした時点で、予算の都合により Close の手前で止めた（§8.2）。

## 1. 課題（Phase 6 で見つかったこと。`docs/phase6.md` §9.4）

1. **Playtester がその場で反応できない。**
   - 入力を先に決める方式では、敵の溜めを見てから避けることができない。
   - 新しい Playtester 4 人が全員部屋 1 で倒れ、Play が空回りした。
2. **ビルドの外にあるプレイヤー向けの説明書（`manual.md`）を、誰も書けない。**
   - サンドボックスにも入らない。
   - その結果、Owner への確認が 6 件出た。説明書のテストも、Studio の中では一度も通らなかった。
3. **`run` が、Goal が `active` のまま出された Owner への確認に気づかない。**
   - 未回答の確認（62）が残ったまま作業が続き、Route が 2 件目（79）を出した。

## 2. 方針

| 問題 | どこを直すか | Studio 本体への影響 |
|---|---|---|
| 1 | プロジェクトのプレイ用コマンド（フィクスチャの `play.py`）に、反応の規則を足す | なし。Playtester は説明書を読んで使う |
| 2 | 説明書をビルドの中（`repo/manual.md`）に移す | 文書に 1 文足すだけ |
| 3 | ランナーの `run` と Route の検証を直す | `studio_run.py`、`execution.md` |

そのうえで、Phase 6 と同じ依頼文・同じ出発点のゲーム・同じ外部の判定（S1〜S3）で、戦闘 Goal を回し直す。

## 3. 設計

### 3.1 反応の規則（問題 1）

プレイ用の入力スクリプトに、時刻つきの入力に加えて、次の形の行を書けるようにする。

```text
when see G within 2 then dash away
when see g within 1.5 then attack
when text "rears back" then dash away
when hearts <= 1 then move away
```

**判定に使うのは、プレイヤーに見えるものだけ。**

- 条件は、その場で描いた画面（文字の地図）と、その時点で表示されたメッセージ行の 2 つだけから判定する。
- ゲーム内部の状態（無敵フラグやタイマーなど）は条件に使えない。
- そのため、規則に従って動くのは「プレイヤーが画面を見て反応する」ことに相当する。

**条件**

| 条件 | 意味 |
|---|---|
| `see <記号> within <距離>` | その記号が、指定した距離（タイル単位）以内に描かれている |
| `text "<語句>"` | そのフレームに、その語句を含むメッセージが出た |
| `hearts <= <n>` | 画面に出ているハートの数が n 以下 |
| `nothing within <距離>` | 敵や弾の記号が、指定した距離以内にない |

**動作**

| 動作 | 意味 |
|---|---|
| `attack` | 斬る |
| `dash <方向>`、`dash away`、`dash toward` | ダッシュする。`away` と `toward` は、条件に合った一番近い記号を基準にする |
| `move <方向>`、`move away`、`move toward`、`stop` | 移動する、止まる |
| `face` | 条件に合った記号の方を向く（移動はしない） |

**人間らしさの制約**

- 規則は上から順に調べ、最初に合ったものだけを実行する。
- 同じ規則は 0.15 秒に 1 回までしか実行しない（人間の反応時間に相当）。
- 規則による入力が無視された場合（攻撃の隙の最中など）、そのことは表示しない。表示が埋まらないようにするためである。

**互換性:** 時刻つきの入力は今までどおり使える。両方を混ぜてもよい。

**限界:** 規則は「その場の判断」をある程度表せるが、人間の手の感覚そのものではない。それでも、入力を先に決める方式（Phase 6）よりは、人間のプレイにずっと近づく。

### 3.2 説明書をビルドの中へ（問題 2）

- フィクスチャの `manual.md` を `repo/manual.md` に移し、`player_visible: repo/manual.md` にする。
- これでエンジニア（書き込み範囲 `@build`）が説明書を更新でき、サンドボックスにも入り、ビルドのテストから読める。

- `studio/templates/project.md` に「ビルドと一緒に変わるプレイヤー向けファイルは、ビルドの中に置く」と書き足す。

ついでに、ボットの書き方を見つけやすくする（Phase 6 §9.4 の 4）。

- `bots.py` は、書式エラーのときに使い方を表示する。
- `repo/README.md` にも書き方を載せる。

### 3.3 Owner への確認を見落とさない（問題 3）

**`run` の変更**

- Goal が `active` のままでも、未回答の Escalation があれば、作成されたときに知らせる（「Studio は並行して作業を続ける」と添える）。
- 停止したときの記録（Owner が読むべきもの、次のコマンド）にも含める。
- 開いている工程が Owner への確認だけになったら、「Owner の回答待ち」として止まる。今は「開いている工程なし」として止まり、Owner が何を読めばよいかが出ない。

**Route の検証の変更**

- 未回答の Escalation があるとき、2 件目は出せない（拒否する）。
- エラーメッセージは「既存の確認（番号）への回答を待つ」よう案内する。
- 同じ質問を重ねて出すこと（Phase 6 の 62 と 79）を防ぐ。

## 4. 退けた案

| 案 | 理由 |
|---|---|
| ランナーが一定時間ごとにゲームを止め、Playtester の executor にその場で入力を決めさせる | 本当の対話に最も近い。ただし 1 回のプレイで executor が数十回必要になり、コストが現実的でない |
| Playtester の実行要求の回数を増やす | 回数を増やしても、反応できない問題は解決しない |
| 外部の判定用ボット（毎フレーム反応する）を、Playtester の代わりに使う | 体験の言葉で語れない。Studio のどの packet にも入れないという原則にも反する |
| Escalation が出たら、すぐに `run` を止める | Studio が意図的に「その間に進める作業」を並行させる場合がある（Escalation のテンプレートにその欄がある）。それを止めてしまう |

## 5. 前提とリスク

- **規則の言葉が足りない場合がある。** Studio がゲームに新しい記号を足しても、説明書に載っていれば使える。ただし「溜めの長さを見て判断する」のような細かい判断はできない。
- **エンジニアは `play.py` も書き換えられる。** そのため規則の仕組みを壊すおそれがある。QA の検証と、外部の判定（反応の規則は使わない）で気づける。
- **反応の規則は、実質的に Playtester が書く簡単なボットになる。** ただし条件は画面に見えるものだけ、反応は 0.15 秒に 1 回までに制限する。結果は外部の判定とも比べる。
- **コスト:** Phase 6 は 120 回の executor でも収束しなかった。今回は上限を **executor 120 回**とし、超えたら止めて報告する。Owner への確認は、Phase 6 と同じく私が推奨案を採用して答える。

### 8.2 実地検証：`runs/p7-combat-run`（Claude、Sonnet）

依頼文「戦闘が単調なので改善したい」（Phase 6 と同じ）を、更新したフィクスチャから `run` した。

**全体**

- 59 オペレーション、executor 101 回、出力 約 109 万トークン。Phase 6 は、Close に届かないまま 120 回を使った。
- 内訳: Designer 14、QA 10、Playtester 4、エンジニア 4、Director 2、Art Director 1、Route 23。
- Owner への確認は 0 件（Phase 6 は 6 件）。
- run は 5 回に分かれた。止まった理由:
  - 4 回は Phase 3 の歯止め（1 回の run で Designer を 4 回目に呼ぼうとした）。
  - 1 回は Claude の利用上限。
- **途中で止めた理由:** Director の Review（2 回目）は「差は小さいが未達成」と判断し、3 周目（文言の修正、部屋 3 の変化づけ、Build、Verify、Play、Review）に入った。最後まで進めると上限の 120 回を超える見込みだったため、ここで止めた。
- 止めた時点のビルドは 0.6.1 で、QA の Verify に 30 FPS・60 FPS の両方で合格している。

**経過**

1. **Observe:** Playtester は反応の規則で 4 回遊び、4 回とも負けた。Grub に近づいて斬り合う規則を書いたためである。ただし「近づく、2 回斬る、1 発もらうの繰り返し」「Grub はどの部屋でも同じ」と、単調さの核心を報告した。
2. **Diagnose、Design:** Designer はボットと trace を使って原因を分析した。Decide は不要と判断した（Designer の権限の範囲内）。
3. **Build（0.5）:** エンジニアは説明書もあわせて更新した。
   - Grub に「溜め、突進、隙」の 3 段階の攻撃を入れた。
   - Spitter は狙いの表示を出してから撃つようにした。
   - 部屋ごとに、Grub の派生（速い型、硬い型）を配置した。
4. **Verify:** Designer が、play とボットで確かめられる数値の受け入れ基準を定め、QA が検証した。**Phase 3 から「未判定」だった数値の基準が、初めて判定された。**
5. **Play（新しい Playtester）:** 規則を使い、7 回で全 5 部屋を遊んだ。
   - 報告の例: 部屋 1 は、警告を見て避ければ楽勝で、2 体目で集中が切れる。硬い型は避けやすく退屈。Spitter は同じループ。部屋 4〜5 は十字砲火。
   - 不具合の疑いも 1 件挙げた（QA が調べ、仕様どおりと判明）。
6. **2 周目:** Diagnose、Design、Build（0.6、0.6.1）、Verify（1 回不合格、のち合格）、Play、Review を 2 回。Review はどちらも「未達成、差は小さい」だった。

### 8.3 外部の判定（Phase 6 と同じ基準。実行前に決めたもの）

| | 出発点（0.4、Phase 7 のバランス） | 停止時点（0.6.1） | Phase 6 の停止時点 |
|---|---|---|---|
| 単純な戦い方（30 / 60 FPS） | 5 部屋突破、失ったハート計 0 / 2 | 2 部屋で倒れ、2 部屋でハート 2、失ったハート計 10 / 10 | 5 部屋突破、0 / 0 |
| 腕のある戦い方（30 / 60 FPS） | 4 / 5 部屋突破、失ったハート計 4 / 2（得をしない） | 5 部屋突破、失ったハート計 1 / 2 | 5 部屋突破、0 / 0 |
| ビルドのテスト、新しい入力 | 通る、なし | 通る、なし | 2 件エラー、なし |
| **判定** | S1 × S2 × S3 ○ | **S1 ○ S2 ○ S3 ○** | S1 × S2 × S3 × |

- 事前に決めた測り方で、**単調さは解消し、腕前が報われるようになった。** 単純な戦い方は通用しなくなり、溜めを見てダッシュで避ける戦い方は、ほぼ無傷で全部屋を突破する。
- **Studio 自身の基準は、外部の判定より厳しかった。**
  - 外部の判定が見ているのは、「単純な戦い方が罰せられ、腕前が報われるか」だけである。
  - Director は、Playtester の報告（「近接の敵はどれも『見て避けて斬る』で済む」）をもとに、敵ごとに違う対処が必要になるまでを目標とした。その差を「小さいが未達成」と判断した。
  - 外部の判定は、この「敵ごとの対処の違い」を測っていない。両者は矛盾しておらず、測っている範囲が違う。

### 8.4 3 つの問題がどうなったか

1. **Playtester の反応:** 解決した。Play の 25 回の実行はすべて成功し、全部屋に届いた。体験の報告も具体的で、Studio の判断（2 周目、Review）を実際に動かした。
2. **説明書:** 解決した。エンジニアが説明書を更新し、テストはサンドボックスで通り、Owner への確認は 0 件だった。
3. **Owner への確認の見落とし:** 今回は確認が 1 件も出なかったので、実地では試していない（決定的テストのみ）。

### 8.5 見つかったこと

1. **長いセッションの出力が切れる。** プレイの出力が上限の 20,000 字を超えると、後ろが切れる。Playtester は部屋 2 と 3 の結末を見られなかった。切るときは末尾を残すべきである（次の候補）。
2. **出発点のバランスを、実装中に調整した**（設計からの逸脱）。
   - 人間に近い反応の速さだと、単純な戦い方では出発点の部屋を安定して突破できなかった。毎フレーム反応するボットなら勝てる。
   - そこで、Grub を 1.2 → 1.0、弾を 2.0 → 1.6 と遅くした。プロジェクト自身の説明（「Grub はたどり着く前に 2 回斬れる」）に合わせるためである。
   - そのため、Phase 6 と Phase 7 の出発点は完全には同じではない。
3. **ボットの書式の誤り**（Designer の最初の 4 回）。使い方の表示を見たあとは、正しく使えた。
4. **コストは依然として大きい。** 101 回のうち Route が 23 回。Review が「未達成」と判断するたびに、1 周（約 15〜20 回）が増える。
5. **歯止めが毎回の run を区切った。** 1 回の run で Designer を 4 回目に呼ぼうとすると止まる。Designer が中心になる Goal では、run がすぐ止まる。
