## 3. 設計

### 3.1 反応の規則（問題 1）

プレイ用の入力スクリプトに、時刻つきの入力に加えて、次の形の行を書けるようにする。

```text
when see G within 2 then dash away
when see g within 1.5 then attack
when text "rears back" then dash away
when hearts <= 1 then move away
```

**判定に使うのは、プレイヤーに見えるものだけ。**

- 条件は、その場で描いた画面（文字の地図）と、その時点で表示されたメッセージ行の 2 つだけから判定する。
- ゲーム内部の状態（無敵フラグやタイマーなど）は条件に使えない。
- そのため、規則に従って動くのは「プレイヤーが画面を見て反応する」ことに相当する。

**条件**

| 条件 | 意味 |
|---|---|
| `see <記号> within <距離>` | その記号が、指定した距離（タイル単位）以内に描かれている |
| `text "<語句>"` | そのフレームに、その語句を含むメッセージが出た |
| `hearts <= <n>` | 画面に出ているハートの数が n 以下 |
| `nothing within <距離>` | 敵や弾の記号が、指定した距離以内にない |

**動作**

| 動作 | 意味 |
|---|---|
| `attack` | 斬る |
| `dash <方向>`、`dash away`、`dash toward` | ダッシュする。`away` と `toward` は、条件に合った一番近い記号を基準にする |
| `move <方向>`、`move away`、`move toward`、`stop` | 移動する、止まる |
| `face` | 条件に合った記号の方を向く（移動はしない） |

**人間らしさの制約**

- 規則は上から順に調べ、最初に合ったものだけを実行する。
- 同じ規則は 0.15 秒に 1 回までしか実行しない（人間の反応時間に相当）。
- 規則による入力が無視された場合（攻撃の隙の最中など）、そのことは表示しない。表示が埋まらないようにするためである。

**互換性:** 時刻つきの入力は今までどおり使える。両方を混ぜてもよい。

**限界:** 規則は「その場の判断」をある程度表せるが、人間の手の感覚そのものではない。それでも、入力を先に決める方式（Phase 6）よりは、人間のプレイにずっと近づく。

### 3.2 説明書をビルドの中へ（問題 2）

- フィクスチャの `manual.md` を `repo/manual.md` に移し、`player_visible: repo/manual.md` にする。
- これでエンジニア（書き込み範囲 `@build`）が説明書を更新でき、サンドボックスにも入り、ビルドのテストから読める。
- Playtester が読めるのは `repo/manual.md` だけで、`repo/` の他のファイルは今までどおり読めない。
- `studio/templates/project.md` に「ビルドと一緒に変わるプレイヤー向けファイルは、ビルドの中に置く」と書き足す。

ついでに、ボットの書き方を見つけやすくする（Phase 6 §9.4 の 4）。

- `bots.py` は、書式エラーのときに使い方を表示する。
- `repo/README.md` にも書き方を載せる。

### 3.3 Owner への確認を見落とさない（問題 3）

**`run` の変更**

- Goal が `active` のままでも、未回答の Escalation があれば、作成されたときに知らせる（「Studio は並行して作業を続ける」と添える）。
- 停止したときの記録（Owner が読むべきもの、次のコマンド）にも含める。
- 開いている工程が Owner への確認だけになったら、「Owner の回答待ち」として止まる。今は「開いている工程なし」として止まり、Owner が何を読めばよいかが出ない。

**Route の検証の変更**

- 未回答の Escalation があるとき、2 件目は出せない（拒否する）。
- エラーメッセージは「既存の確認（番号）への回答を待つ」よう案内する。
- 同じ質問を重ねて出すこと（Phase 6 の 62 と 79）を防ぐ。

## 4. 退けた案

| 案 | 理由 |
|---|---|
| ランナーが一定時間ごとにゲームを止め、Playtester の executor にその場で入力を決めさせる | 本当の対話に最も近い。ただし 1 回のプレイで executor が数十回必要になり、コストが現実的でない |
| Playtester の実行要求の回数を増やす | 回数を増やしても、反応できない問題は解決しない |
| 外部の判定用ボット（毎フレーム反応する）を、Playtester の代わりに使う | 体験の言葉で語れない。Studio のどの packet にも入れないという原則にも反する |
| Escalation が出たら、すぐに `run` を止める | Studio が意図的に「その間に進める作業」を並行させる場合がある（Escalation のテンプレートにその欄がある）。それを止めてしまう |

## 5. 前提とリスク

- **規則の言葉が足りない場合がある。** Studio がゲームに新しい記号を足しても、説明書に載っていれば使える。ただし「溜めの長さを見て判断する」のような細かい判断はできない。
- **エンジニアは `play.py` も書き換えられる。** そのため規則の仕組みを壊すおそれがある。QA の検証と、外部の判定（反応の規則は使わない）で気づける。
- **反応の規則は、実質的に Playtester が書く簡単なボットになる。** ただし条件は画面に見えるものだけ、反応は 0.15 秒に 1 回までに制限する。結果は外部の判定とも比べる。
- **コスト:** Phase 6 は 120 回の executor でも収束しなかった。今回は上限を **executor 120 回**とし、超えたら止めて報告する。Owner への確認は、Phase 6 と同じく私が推奨案を採用して答える。
