## 1. 課題（Phase 7 の実測。`runs/p7-combat-run`）

1. **ファイル全体を毎回書き直すので、出力が重い。**
   - Phase 7 の出力は約 109 万トークンだった。ファイル本文として書き出した量は次のとおり。

     | 書き手 | 書き出した量 | 内容 |
     |---|---|---|

     | Designer | 約 25 万字 | 設計書、17 回 |
     | Route | 約 17 万字 | goal.md、25 回 |

   - たとえばエンジニアは、数行を直すたびに 800 行のゲームと 1,150 行のテストを全部書き直していた。
   - 量の見積もりでは、全出力のうち 15〜20% がこの重複にあたる。残りの大部分は推論（考える過程）である。
2. **長い実行結果の末尾が切れる。** 出力を 20,000 字で切るときに後ろを捨てていたので、Playtester はプレイの結末を見られなかった。
3. **戦闘 Goal が Close していない。** Studio 自身の Review は「差は小さいが未達成」と判断し、3 周目に入る手前で止めた。

## 2. 方針

1. **部分編集を書けるようにする**（実行環境の出力規約の追加）。
   - 「この文を、この文に置き換える」という形の編集ブロックである。
   - ファイル全体のブロックも今までどおり使える。
2. **出力を切るときは、先頭と末尾の両方を残す。**
3. **Phase 7 の続きから、戦闘 Goal を Close まで進める。**
   - Phase 7 の記録はそのまま残す。そのコピーで続ける。
   - 部分編集でコストがどれだけ下がるか、Studio が自分の基準まで届くかを確かめる。

## 3. 設計

### 3.1 編集ブロック

```text
<<<EDIT repo/game.py
<<<<<<< SEARCH
GRUB_SPEED = 1.0
=======
GRUB_SPEED = 0.9
>>>>>>> REPLACE
>>>END
```

**規則**

- 1 つのブロックに、置き換えの組をいくつ書いてもよい。上から順に当てる。
- `SEARCH` の文は、その時点のファイルにちょうど 1 回だけ現れなければならない。
  - 見つからない場合は拒否する。
  - 2 回以上現れる場合も拒否し、「前後の行を含めて、1 か所に決まるようにする」よう案内する。
  - 空の `SEARCH` は使えない。
- 対象は既存のファイルに限る。新しいファイルはファイル全体のブロックで書く。
- 1 つの答えで、同じファイルにファイル全体のブロックと編集ブロックを混ぜてはいけない。
- 当てた結果のファイル全体を、今までと同じ規則で検証する。書き込み範囲、成果物の形式、ロールのポリシーなどである。
- 実行要求（`@run`）の変更案にも使える。その場合は、直前の変更案に対して当てる。
- 記録には、出力そのもの（編集）と、書き込んだファイル全体のハッシュを残す。

**どこに書くか**

- `studio/execution.md`: 出力規約と executor への指示。これは packet に毎回入る。
- 仕組みはツールに依存しないので、Studio 本体の文書に置いてよい。

### 3.2 出力の切り方

- 実行結果が上限（20,000 字）を超えたら、先頭 14,000 字と末尾 6,000 字を残す。
- 間には「◯字を省略」と入れる。
- 最後の数行（プレイの結末、テストの結果）が必ず見えるようになる。

### 3.3 Phase 7 の続きから Close まで

- `runs/p7-combat-run` を `runs/p8-combat-run` にコピーし、記録も含めて引き継ぐ。
- Phase 8 のランナーで `run` を続ける。いま開いているのは、22a（Build）と 22b（Design）である。
- 予算は executor 80 回を追加とする（合計 181 回まで）。超えたら止めて報告する。
- Owner への確認には、これまでどおり私が Studio の推奨案を採用して答える。

## 4. 退けた案、見送った案

| 案 | 理由 |
|---|---|
| unified diff 形式（行番号つきの差分） | 行番号や前後の行の数え間違いが起きやすく、LLM には不向き。置き換え方式のほうが失敗しにくい |
| 編集ブロックだけにして、ファイル全体のブロックをなくす | 新しいファイルや大きな書き換えでは全体のほうが確実。両方を残す |
| 外部の判定に「敵ごとに違う対処が必要か」を加える（Phase 7 の候補 2） | **見送り。** Studio の Review がすでにこの観点を厳しく見ている。外部の判定をそれに合わせて作ると、Studio の言葉に判定を寄せることになり、独立性が下がる。Close のときに S1〜S3 を測り直し、Studio の主張と照らし合わせる |
| 推論のトークンを減らす（モデルやプロンプトを変える） | 出力の大部分は推論だが、品質に直結する。今回は重複の書き出しだけを対象にする |

## 5. 前提とリスク

- **SEARCH の書き間違い**（空白や引用符の違い）で拒否が増えるかもしれない。エラーメッセージで、該当しない箇所と直し方を示す。拒否が多ければ、比較時に行末の空白を無視するなどを検討する。
- **編集ブロックを使うかは executor 次第。** 使わなくても今までどおり動く。使われた割合を測る。
- **Phase 7 の続きの最初の数ステップは、Phase 7 の packet の形式で始まる。** 編集の説明は executor への指示の一部なので、Phase 8 の最初のオペレーションから入る。
