# Phase 9 設計案：長い packet の末尾で書式を思い出させ、ファイルへの混入を防ぐ

状態: **設計案（承認待ち）**

## 1. 課題（Phase 8 の実測。`runs/p8-combat-run`、`docs/phase8.md` §8.4〜§8.6）

1. **QA が、Handoff の節を欠いた最終回答を 3 回出した**（076、098、105）。
   - 3 回とも、実行要求（run round）の直後の最終回答だった。
   - そのときの packet は最大 26 万字で、末尾には約 3,600 行の実行結果が並んでいた。
   - Handoff のテンプレートは packet の中ほど（全体の約 4 割の位置）にある。executor は自分の報告の形（`## Verdict`、`## 1. run_tests` など）で書き、必須の節を落とした。
   - 拒否のメッセージを見たやり直しでは、3 回とも通った。つまり、規則を知らないのではなく、長い packet の末尾で忘れている。
2. **ツールの呼び出し記号が、ファイルに入り込んだ。**
   - executor の出力に、`</invoke>` や `</parameter>` が混ざることがある。記録の中に 10 回あった。
   - そのうち 1 回はファイルのブロックの中に入り、D-007 の末尾に `</parameter>` が残った（Phase 7）。
   - Phase 8 では、崩れた編集記号も 2 回ファイルに入った。これは EDIT の REPLACE の中だけを対象にして直した（`519bfcd`）。ファイル全体のブロックに入った場合は、まだ防げない。
3. **Decision は書いた後に直せないことを、Studio の文書が言っていない。**
   - ランナーは、既存の Decision への書き込みを拒否する（新しく作ることだけを許す）。
   - しかし、Route が読む `studio/` の文書には、そのことが書かれていない。
   - そのため Route は、D-007 の 1 行の削除を 2 回 Designer に頼んだ。Designer は 2 回とも `question` を返し、歯止めで run が止まった。

## 2. 方針

1. **Step の packet の末尾に、答えの形を短く書く。** 必須の節と、出力の形式だけを書く。
2. **書き込むファイルに、混入した行がないかを確かめる。**
   - 対象は、編集記号とツールの呼び出し記号である。
   - ファイル全体のブロックにも、EDIT ブロックにも同じ確認をかける。Phase 8 の REPLACE だけの確認は、これにまとめる。
3. **Decision は書いた後に変えず、新しい Decision で置き換える、と文書に書く。**

## 3. 設計

### 3.1 packet の末尾の「答えの形」（課題 1）

- Step の packet の最後（読み込んだファイルと実行結果の後）に、次の節を足す。

  ```text
  ## Your answer

  - The outgoing Handoff keeps every section of studio/templates/handoff.md, in order:
    Task, Context, Findings, Decisions already made, Constraints, Open questions,
    Expected output, Load. Put your own report inside Findings.
  - Wrap every file in <<<FILE path … >>>END or <<<EDIT path … >>>END (studio/execution.md).
  ```

- 節の名前は、ランナーが検証に使う必須の節の一覧から、テンプレートの順に作る。一覧が変われば一緒に変わる（任意の `## Sender assessment` は含めない）。
- 実行要求の後の packet でも、毎回この節が最後に来る（実行結果は、この節より前に入る）。
- Route、Intake、Resume の packet には足さない。どれも短く、今回の失敗も起きていない。

### 3.2 混入した行の確認（課題 2）

- 書き込むファイルごとに、元のファイルになかった行で、次のどれかに当たるものがあれば拒否する。
  - 編集記号に似た行（`<<<<<<< SEARCH`、`>>>REPLACE` など。Phase 8 と同じ判定）。
  - ツールの呼び出し記号だけの行（`</invoke>`、`<parameter name="…">`、`</parameter>` など）。
- 元のファイルに同じ行がすでにある場合は、拒否しない。混入した行を消す編集も、そのまま通る。
- エラーでは、ファイルと行を示し、「出力の書式の一部がファイルに入っている。取り除く」と案内する。
- 実行要求の変更案にも、同じ確認をかける。サンドボックスに混入した行が入らないようにするためである。
- ランナー（`scripts/studio_run.py`）に置く。`studio/` には書かない（ツールの名前を出さないため）。

### 3.3 Decision は置き換える（課題 3）

- `studio/orchestration.md` の Decision の段落に、1 文足す。
  - 「Decision は書いた後に編集しない。変えるときは、`supersedes:` をつけた新しい Decision を書く。誤字や混入した行も同じで、Role に直させない。」
- ランナーの動きは変えない（すでに新規作成だけを許している）。

## 4. 退けた案、見送った案

| 案 | 理由 |
|---|---|
| Handoff のテンプレートを packet の末尾に移す | テンプレート全体（約 60 行）を末尾に置くと、毎回の packet が長くなる。必須の節の名前だけで足りる |
| 欠けた節を、ランナーが空の節として補う | 中身のない Handoff が通ってしまう。次の Role が困る |
| Decision の訂正手段（内容を変えない直しだけを許す） | **見送り。** 今回の 1 行は混入によるもので、§3.2 で起きなくなる。誤字の訂正だけのために、「内容を変えない」の判定を作るのは重い |
| 人間のプレイヤーによる確認の手順（Phase 8 の候補 4） | **見送り。** 人間のプレイヤーが必要で、この環境では検証できない |
| 新しい Goal を最初から走らせて確かめる | 課題 1 は、長い packet でしか起きない。短い Goal では再現しない。§7 の再送のほうが直接に確かめられ、安い |

## 5. 前提とリスク

- **「答えの形」が効かないかもしれない。** その場合は §7 の再送で分かる。効かなければ、実行結果を packet の中ほどに移す案を次に試す。
- **混入の判定が、正しい行を拒否するかもしれない。** 対象を「記号だけの行」に絞り、元のファイルにある行は許すので、起きにくい。ゲームのコードやマークダウンで `<parameter …>` だけの行を書くことは、まずない。
- Phase 8 までの記録は変えない。D-007 と goal.md の Outcome に残った行も、記録としてそのまま残す。

## 7. 検証計画

**決定的テスト**

- packet の末尾:
  - Step の packet の最後が「答えの形」の節で、節の名前が必須の節の一覧と一致する。
  - 実行要求の後の packet でも、実行結果より後に来る。
- 混入した行:
  - ファイル全体のブロック、EDIT ブロック、実行要求の変更案のどれでも拒否される。
  - 元のファイルにある行と、混入した行を消す編集は通る。
- 記録の再生: Phase 7 で D-007 に入った出力（`p7-combat-run` の 043）を新しい確認にかけると、拒否される。
- 既存の 110 件がすべて通る。

**再送による比較（Claude、Sonnet。executor 12 回）**

- QA が節を欠いた 3 つの packet を、記録から取り出す（076 の 3 回目、098 の 4 回目、105 の 2 回目）。
- それぞれを、「そのまま」と「末尾の節を足したもの」で 2 回ずつ送る（3 × 2 × 2 = 12 回）。
- 答えの Handoff に、必須の節がすべてあるかを数える。
- 確かめること: 末尾の節で、節の欠けがなくなるか、減るか。
  - 答えが最終回答ではなく、さらに実行を求めた場合は、判定から除いて数を報告する。
