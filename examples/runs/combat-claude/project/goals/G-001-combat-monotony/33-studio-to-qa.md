# 33: studio → qa — 模擬ビルド 0.5 の再検証(F-1、V7、V10、V12(c)。あわせて V1〜V12 の回帰確認)

## Task

模擬ビルド `sim/build-0.5.md` を、仕様の受け入れ基準に照らして再検証する。重点は次の4点。そのうえで V1〜V12 を回帰として確認する。

1. **F-1**: 突進型 Grub の再突進(Windup)の待ち時間の起点。
2. **V7**: Grub の Chase 速度の数値(部屋ごと)と、「遠い方」の2つの角が同距離のときの扱い。
3. **V10**: プレイヤー側の数値(攻撃、ダッシュ、被弾、無敵)が変わっていないこと。
4. **V12(c)**: 同じ波の複数スロットの出現位置の待ちが、同時に始まること。

## Context

G-001(戦闘の単調さの改善)。D-008 により、このプロジェクトでは模擬ビルドに基づいて判定する。ビルドは `sim/build-0.5.md` で、前回(0.4)の検証後に更新されたものとして扱う。この操作の入力にビルドの中身はなく、Studio は内容を確認していない。読めない場合や、記述が仕様の判定に足りない場合は、推測で pass にせず報告する。結果は実機の証拠ではない。

前回の検証(Handoff 30)では、V1〜V12 に fail はなく、V7(Grub の速度の数値、遠い角が同距離のときの規則)と V10(プレイヤー側の数値)の一部がビルドの記述から確認できず、pass にできなかった。基準外の食い違い F-1 もあった。

## Findings

検証の基準は仕様にある。以下は仕様から導かれる期待値で、実装の説明ではない。本文は要約せず、`design/combat.md` を読むこと。

- **F-1(仕様 §3.3)**: 突進型 Grub が次の Windup に入れるのは、前回の Recovery が終わってから 2.5 s 以上たった後。起点は Recovery の終了で、前回の Charge の終了ではない。Charge の終了時刻を t とすると、Recovery は t から 0.8 s 続き、次の Windup は早くても t + 0.8 + 2.5 s 以降になる。ビルドの記述が、起点を Recovery の終了とも Charge の終了とも読める、または読めない場合は、その事実を報告する。
- **V7(仕様 §4.1、§4.3、D-005)**: Grub の Chase 速度は部屋 1〜5 で 2.0 / 2.0 / 2.2 / 2.2 / 2.4 タイル/s。「FL / FR のうち遠い方」は、出現を決める時点のプレイヤーの位置から、各スロット座標までの距離(中心間)で比べる。距離が等しいときは FL を選ぶ。選んだ後は選び直さない。
- **V10(仕様 §1)**: プレイヤー側の数値(攻撃、ダッシュ、被弾の硬直と無敵など)は、この変更で変わらない。ビルドが変更点を列挙している場合は、そこにプレイヤー側の数値の変更がないこと。数値の記述がある場合は仕様 §1 と一致すること。
- **V12(仕様 §4.1、D-009)**: 波 N の次の波の条件(K、T)は、波 N の全員が出現中に入った時点から調べ始める。出現位置の待ちの敵は「生きている敵」に数えない。(c) 同じ波の複数スロットの出現位置の待ちは、その波の出現を決めた時点から同時に始まり、スロットごとに別々に数える。待ちの間に、先に出ていた敵を倒すと、次の波はすぐ出る。
