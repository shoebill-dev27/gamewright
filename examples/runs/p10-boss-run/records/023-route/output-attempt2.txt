# 19: studio → technical-director — 限定調査でBuild開始条件を補完する

## Task

16の技術計画をD-020に従って補完する。既存資料・実行環境・利用可能資源を調査し、Build開始の五条件について確認済みの証拠、残る不足、解決担当・経路をStudioへ返す。

## Context

Ownerは連続ラン、第5部屋の単体ボス、先頭からのretryをD-015で承認した。詳細仕様と基準適用はD-017／D-019で確定済み。16は静的な技術計画で、実行基線・回帰正本・実機環境・費用承認が未確認のためBuildを保留した。

18とD-020は、desktopのkeyboard／gamepad操作・表示に必要な最小ホストを既存要件の実現作業としてPlanに含めた。ただし費用・リスクの承認内認定ではない。現時点で承認超過や供給不能は確定しておらず、OwnerへのEscalationは開いていない。

## Findings

今回の調査対象は次のとおり。

1. 実行対象：gitルート、対象commit、指定sha `27fe16268ac8`との関係、作業差分の有無、0.4／0.6表記の由来。差分の有無を確認する際も秘密情報の本文を出力しない。
2. 実行基線：Python版・既存依存、既存tests、player／trace、各botの30/60 FPS結果。実行条件、終了理由、失敗、未実施を区別する。実行方法はrepo/README.mdとrepo/manual.mdに従い、既存スクリプトを確認して選ぶ。
3. 回帰正本：combat.md、step44・46・68・72・94、関連Decision、実テストを読み、保持／終了／置換先と仕様IDを対応させる。16で未読だった正本とD-011〜D-014を今回のLoadに追加した。
4. 実機供給：利用可能なdesktop OS・表示環境、keyboard／gamepad機器、既存依存、導入権限、独立検証の供給元・利用条件を確認する。調査環境に見当たらないことだけで、プロジェクト全体に存在しないと断定しない。
5. ホスト方式：共通Sessionへの接続、入力・表示・記録、保持入力解除、30/60 FPS、実時間pause確認の最小方式と制約・代替案を示す。技術方式の選択はTechnical Directorが行う。
6. 費用・承認：ホスト・統合・独立QA／Art／Play・Designer判断・修正／再検証を含め、前提、除外、不確実性、金銭費用、既存承認との対応を整理する。

16のBuild準備〜統合11.5〜20人日にはホスト2〜4人日を含む。独立QA・Art・Play込みの提示済み部分は15〜26人日だが、総費用でも承認済み予算でもない。新たな実行・供給・費用の証拠は今回まだない。

- D-011〜D-014：表示・第3部屋・文言と過去Goalの判断。履歴を改変しない。

## Constraints

- ゲーム・ホストの実装、新規依存導入、購入、外部費用の確約を行わない。
- Owner request、Interpretation、仕様、既存Decisionを変更しない。project.mdも変更しない。
- OS・機器・予算上限・権限・独立検証枠を推定で補わない。既存資源の発見と新たな供給の確約を分ける。
- 秘密情報、環境変数の値、個人情報を出力・記録・後続資料へ含めない。
- 実行未確認を成功とせず、模擬入力やheadlessをV2の独立実機検証の代用にしない。
- 追加難度ゲートはD-019に基づく実測後のDesigner判断とし、未設定だけを新たな開始阻害にしない。
- 逐次実装と、独立QA→限定Art Verify→独立Play→Designer実測後判断→Reviewの順序を維持する。明白な対処不能・到達不能はPlay前にDesignerへ戻す。
- studio/orchestration.mdのEscalationトリガーとLoop limitsも照合する。同じ不足を新情報なしに再質問する経路を作らない。

取得不能なら、実際の制約と試した確認経路、必要な資料・checkout・実行権限・OS・機器・検証枠、回答者と解決経路を具体化する。調査結果を返したことと開始条件の充足を区別する。

購入・追加予算・権限付与・Roleでは確保できない環境、または費用承認根拠の不足が具体化した場合は、Game Directorへ戻せる brief をFindingsに含める。判断対象を「必要な供給・費用を伴う現行仕様の継続」にまとめ、現実的な2〜3案、各案の必要物・費用幅・未確定部分・後続ルート、推奨と再検討条件を示す。Studioが次にGame Directorへルーティングする。
