# 27: studio → gameplay-engineer — 部分実装からボス・連続ランのBuildを完成する

## Task

26の終端基盤を現状ソースで確認し、承認仕様と適用可能な既存計画に従って残りのBuildを完成する。ボス・弾属性から進め、全機能と必要試験・説明更新・測定を整えてstudioへ返す。

## Context

Owner requestは「最後に手応えのあるボス戦がほしい」。D-015〜D-019で連続ランと単体ボスの範囲・仕様・評価方針を確定し、D-021で現状repo/のテキスト実行とStudio内検証によるBuildが承認された。

26は部分成果の報告であり、全Build完了ではない。新しい仕様質問、供給要求、開始承認待ちはない。Studioは次の継続Buildを開き、独立QA投入をまだ行わない。

## Findings

26の報告内容：

- game.pyの終端確定・死亡優先・残弾と予兆消去・終端後凍結。
- play.pyの終端後ループ終了。
- test_terminal.pyの両FPSを扱う3試験。
- 変更前基線は24の69 tests成功。26が参照する実行証拠はRound 1が30秒timeout、Round 2が72 tests成功。Studioによる再実行・独立検証ではない。
- ボス、RunSession、pause/resume、retry、入力・表示契約、説明更新、対応bots、通常ラン測定は未完了。

現状ファイルを正本として26の部分成果の反映状況を確認する。未反映なら仕様・計画に沿って必要な変更を含める。26にある一時的な`@run-results`は次Stepの入力として要求せず、永続した報告と現状ファイルを用いる。過去の成功を今回の完成版の合格証拠として扱わない。

## Decisions already made

- D-001：戦闘入力はattackとdash。
- D-015〜D-017：第1〜4部屋を連続して進み、第5部屋を単体ボスへ置換。回復・継承・死亡優先・最初からのretryを含む。
- D-018〜D-019：旧第5部屋に依存する集計の適用終了と代替評価。共有回帰は保持する。
- D-021：現状repo/のテキスト表示・script実行で進める。指定sha確認、実機供給、gamepad実機検証、外部配員、見積もり取得を開始条件にしない。

## Constraints

- 第1〜4部屋の構成と共有戦闘パラメータを保持する。
- 新戦闘入力、ボス専用チェックポイント、時間合わせのHP増加・待機を追加しない。
- 30/60 FPSを対象とする。購入・外部委託・追加金銭を使わない。
- 16・20の計画はD-021と整合する部分を適用する。実機・外部供給・見積もり要求へ戻さない。
- 既存計画に従い、ボス・弾属性→Session→parser・表示・説明→対応bots・測定の順で逐次進める。
- 独立QA→限定Art Verify→独立Play→Designer実測後判断→Reviewを維持する。自分の試験で独立検証を代替しない。

## Open questions

新規の仕様・計画質問はない。実装中に仕様の曖昧さが判明したらDesignerへ、計画が成立しない場合はTechnical Directorへ戻すためstudioに具体的な根拠を返す。実測値の評価・追加数値ゲートの要否は後続Designerが判断する。

## Expected output

`studio`宛てのBuild結果Handoffを作成する。

- 完成した変更、未完了事項、仕様のR/B/T/C/V各基準との対応を区別する。
- 旧assert移行、共有戦闘回帰、終端・Session・pause/retry、両FPSの試験結果を示す。実行コマンド、入力、終了状態と測定条件を再現可能に残す。
- player/trace表示、manual/README、対応botsを仕様どおり完成する。
- 対応botの両FPS、開始hearts 3/2別比較と、正規敵撃破による同一試行の通常ラン到達・終端・所要時間の測定を残す。独立診断scriptを通常ラン到達の証拠にしない。
- 独立QAが仕様・受入基準・buildから検証できる手順を記載する。実装理由や自己評価は独立した`## Sender assessment`へ置く。
- 明白な対処不能・到達不能を認めた場合は、その証拠を明示してstudioへ返す。

全Buildが完了するまでQA投入可能としない。残作業がある場合は部分成果と明記し、完成と区別する。
