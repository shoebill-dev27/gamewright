# G-001: Player takes damage while dashing

## Owner request

> ダッシュ中なのにダメージを受けることがある。再現できるので直してほしい。

## Interpretation

Success condition: when the player is in the state the game defines as "dashing" (and the design documents say the player should not be hurt then), no damage is taken. The Owner can no longer reproduce the case where a dashing player takes damage, at both 30 and 60 FPS.

Whether "dash should protect the player" is already specified (design/combat.md covers damage and invulnerability rules) was not read at Intake. The first step checks it. If the documents say dash is invulnerable, or protected for some part of the dash, this is a defect. If they leave it undefined or contradict the Owner's expectation, the route changes (see Unknowns).

Out of scope: changing the combat kit, adding input buttons (D-001), rebalancing damage or dash tuning beyond what the fix requires, and new enemies or rooms.

The Owner says the problem is reproducible but gave no steps. The conditions (which enemy, which part of the dash, frame rate) are unknown and are for QA to find.

## Unknowns

Entry questions from development-loop.md:

- **Observe**: Not reproduced first-hand by the Studio, and the Owner gave no conditions. Stage created: `qa` with `reproduce-defect`. This is a defect, not an experience problem: damage during dash is either contradicted by the design documents or plainly broken. The Role that handles a mismatch with the design documents is `qa`.
- **Diagnose**: Root cause is a defect-cause question owned by `gameplay-engineer`. It happens inside Build, so there is no separate stage.
- **Decide**: No real choice of direction is visible. Tentative: only if QA finds the design intent is ambiguous in a way that implies a direction or priority change.
- **Design**: Skipped for now on the assumption that combat.md already specifies dash invulnerability. This was not verified at Intake. Tentative: needed if QA reports that the intended behavior is undefined or ambiguous (for example, the exact frames of the dash that are invulnerable).
- **Plan**: Skipped. A fix to existing dash/damage rules is expected to be local. Tentative: needed if the root cause turns out cross-system or risky, or if verification fails twice on the same criterion.
- **Build**: Needed if QA confirms a defect.
- **Verify**: Always after Build.
- **Play / Review**: Skipped. This is a defect with a specified behavior, not an experience Goal, and no direction Decision is involved.

# 01: studio → qa — Reproduce "damage taken while dashing" and write a defect report

## Task

Reproduce the reported defect in the current build and write a precise defect report with acceptance criteria. Determine from the design documents what the intended behavior is.

## Context

Goal G-001. The Owner reported (original wording in Japanese): "Sometimes I take damage even while dashing. It is reproducible, so please fix it." No reproduction steps were provided, so which enemy, which part of the dash, and which frame rate are all unknown. The game is a dry-run project: "running the build" means reading `sim/build-0.3.md`.

## Findings

Nothing yet. No Role has looked at this. The Studio has not read `design/combat.md`, which per the project's design index contains the damage and invulnerability rules. It is not known whether the documents say dash makes the player invulnerable, fully or partly.

## Decisions already made

None.

## Constraints

- The game must play correctly at both 30 and 60 FPS. Check whether the defect depends on frame rate.
- No new input buttons beyond attack, dash and pause (D-001). This limits any later fix; it is not for you to resolve.
- Do not propose or implement a fix. Root cause belongs to the gameplay engineer.

## Open questions

- What does the design say should happen to damage during a dash (fully invulnerable, a window of invulnerability, none)? If the design is silent, ambiguous, or contradicts the Owner's expectation, say so explicitly in the report rather than choosing an interpretation.
- Under which exact conditions does damage during a dash occur (enemy type, timing within the dash, frame rate, start/end of the dash)?
- If you cannot reproduce it from the build and documents, say exactly what is missing (conditions only the Owner can supply).

## Expected output

A defect report written in the outgoing Handoff (templates/handoff.md): reproduction steps, observed vs. expected behavior with the design source quoted, frequency/conditions, severity, and player-observable acceptance criteria, including a check at 30 and 60 FPS.

Set `to` by outcome:
- Defect confirmed and intended behavior specified: `gameplay-engineer`.
- Intended behavior undefined or ambiguous: `game-designer`, with the open point stated.
- Not reproducible or Owner information needed: `studio`, `outcome: question`, stating what is missing.
