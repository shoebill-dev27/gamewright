# G-001: Improve monotonous combat

## Owner request

> 戦闘が単調なので改善したい

## Interpretation

Success condition (qualitative): a player from the project's player profile experiences combat in the current build as varied and engaging rather than repetitive. Playing a run involves meaningful moment-to-moment variation in how the player positions, times and responds to enemies. Numeric thresholds belong to Design; the final verdict belongs to Review.

Constraints that shape any solution:
- Pillar 1 and D-001: combat stays one-button (attack + dash). No new input buttons without Owner approval. Variety must come from positioning, timing and enemy behavior.
- Readable threats (pillar 3) and 30/60 FPS correctness must be preserved.
- Small team: prefer reusing existing systems.

Out of scope: new input buttons or a larger player kit, changes to run length, new biomes or rooms unrelated to combat variety, and non-combat systems.

Not an immediate escalation: the Goal does not conflict with the vision or D-001. It must be solved inside them. If Diagnose finds that the only viable fixes need a new button or change a pillar, that triggers an Owner escalation then.

## Unknowns

Entry questions from `development-loop.md`:
- Observe: has the problem been observed first-hand? No. It is an experience problem (the game may work as specified but feel wrong), so `playtester` observes. The Owner's wording is not given to the Playtester, to avoid confirming a hypothesis.
- Diagnose: is the cause understood? No. What makes the combat feel monotonous is unknown (enemy behavior, kit depth, room design, pacing). Stage created.
- Decide: is there a real choice of direction, priority or scope? Probably, once the diagnosis offers options. Tentative.
- Design: is the intended behavior specified well enough to build? Not for any change yet. Tentative on the chosen option.
- Plan: tentative. Needed only if the chosen change is non-obvious, risky or cross-system.
- Build: tentative. Needed only if the chosen option changes the game.
- Verify: always after Build (tentative with Build).
- Play: the Goal is about how the game feels, so a Playtester re-evaluates after Build (tentative with Build).
- Review: experience Goal, so the Game Director judges the outcome. Planned.

Skipped: none yet. The Project Context does not answer any entry question.

# 01: studio → playtester — Play the current build, focusing on combat, and report your experience

## Task

Play the current build as a player from the profile below, paying attention to combat. Report what you observe and experience, using only what a player can see and feel.

## Context

This is a first playtest of the current prototype build. No implementation history or expected result is provided, on purpose.

How to run the build: this is a dry-run project with no real executable. "Running the build" means reading `sim/build-0.3.md` and playing through it as described there.

Player profile (from the Project Context): action players who want short, intense runs. They are comfortable with dodging and spacing, and are not interested in memorizing combo lists. They mostly play with a gamepad.

Play focus: combat.

## Findings

None (this is the first step).

## Decisions already made

None.

## Constraints

- Report observable experience only: what you saw, did and felt, and when. Do not guess at causes in the code or design.
- Use only the build and the player profile. Do not open design documents, repository notes or Decisions.
- You have no authority over the game's design. Report accuracy matters; fixes are not asked for.

## Open questions

None.

## Expected output

An observation report following the `playtest-session` skill: what was played, the observed combat experience in sequence, moments that stood out (good or bad), and any behavior that looks plainly broken (crash, stuck state), listed separately. Address the report to `game-designer`, who runs Diagnose next. The Studio will add the Owner's original report for the Designer when routing.
