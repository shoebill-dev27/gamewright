# 18: studio → gameplay-engineer — Make the hit-stun input behavior observable and consistent with D-003 (verification blocker)

## Task

State exactly how the build handles a dash or attack pressed during hit-stun, so that it is ignored and not buffered (D-003). Make the change if the current behavior differs. Record the result in build notes in player-observable terms. Also report the code-side values listed below. Do not change anything else.

## Context

Goal G-001 (combat monotony). The dash/hit invulnerability fix (handoff 08) is being verified by `qa`. QA's second attempt (handoff 15) found that everything described in `sim/build-0.4.md` is consistent with the six criteria in `05-qa-to-studio.md`. QA could not give a verdict on one case: a dash (or attack) pressed during the 0.3 s hit-stun. `sim/build-0.4.md` says only "behaves as it did in 0.3", and `sim/build-0.3.md` does not describe it. D-003 (decided by the designer) requires such input to be ignored, not buffered. Nothing fires during hit-stun or when it ends.

This is the second `question` from step 4a, but for a different missing input. The first was a missing build file, and the second is a missing build behavior. If QA again hands back for the same missing hit-stun observation, the Studio escalates to the Owner.

## Findings

From QA (handoff 15):
- The hit-stun dash press is undescribed in both builds. Neither is observed to be "ignored" or "buffered".
- `sim/build-0.4.md` has the heading "Simulated build 0.3.1" while the file is named 0.4. The Studio needs to know whether they are the same build.
- Flicker and sound cues around the hit and dash are not mentioned in the build text, so QA could not check them.
- The build files are prose and give no repeat counts or measured boundary timings.

## Decisions already made

- D-001: one attack button plus dash; no new input.
- D-003: input during hit-stun is ignored, not buffered. Hit invulnerability and dash invulnerability are independent timers.
- D-004: Phase 2 technical approach (timestamps on the accumulated game clock, not frame counts). Phase 1 is a separate Build that waits for this fix to pass verification.

## Constraints

- Scope is the hit-stun input handling only. This is not the start of Phase 1; the Phase 1 wave scheduler, marker and room tables are not part of this step.
- The fix must be correct at 30 and 60 FPS. Use timestamps, not frame counts.
- Dry-run project: state the change exactly (what changes, where, how to exercise it). The change then counts as made and the simulator updates `sim/`. If nothing needs to change, say so, and say what the build does, in observable terms.
- If the spec is ambiguous, hand back. Do not decide it yourself.
- No new input buttons.

## Open questions

Answer in your handoff:
1. What does the build do today when dash is pressed during hit-stun, and when attack is pressed? Does anything fire during hit-stun, at its end (buffer), or both?
2. Is `sim/build-0.4.md` (heading "0.3.1") the latest build?
3. Report these code-side values, as the Technical Director and Art Director need them (technical-director handoff 16, task 0, and art-director handoff 17): Grub speed, player speed, projectile speed and range, hearts, room size in tiles, Grub and player hitbox sizes, whether a spawn effect or spawner exists, and where the Flinch is implemented. A value that `sim/repo-notes.md` does not contain should be reported as "not in the code notes".
4. Are there flicker or sound cues for hit invulnerability or dash invulnerability? Describe them in observable terms, so QA can check them.

## Expected output

A handoff with the change (or "no change needed") and the answers above, in observable terms. **Address the result to `studio`**, so that the Studio can compose a clean verification Handoff for `qa` without implementation history. Put your own reasoning only in `## Sender assessment`; it is removed before QA receives the handoff.

# 19: studio → game-designer — Adjust the Phase 2 spec from the Technical Director and Art Director answers

## Task

Update the Phase 2 part of `design/g001-combat-escalation.md` (Lunge Grub and Fan Spitter) using the answers in handoffs 16 and 17. Answer the four open spec questions and point the spec at `design/g001-telegraph-visuals.md`. Keep the Phase 1 spec stable; do not reopen it.

## Context

Goal G-001 (combat monotony). D-002 chose encounter escalation first (Phase 1), then enemy behaviors that demand movement and the dash (Phase 2). In handoff 11 you asked for feasibility and cost (Technical Director) and for telegraph visuals (Art Director) before Phase 2 is built. Both have answered:

**Technical Director (handoff 16, with D-004):**
- Both behaviors are feasible and cheap. The Fan Spitter is the cheaper one, and the Lunge Grub is small to medium. Neither needs to be dropped for cost. The repositioning Spitter is rejected on cost, so Fan Spitter it is (D-004).
- The existing 0.2 s **Flinch** (a player hit interrupts any enemy action; it is in the code but not in `combat.md`) conflicts with spec 4.1. One swipe during wind-up would cancel the telegraph, and recovery would be shortened to about 0.2 s. The cheap fix is a per-state flinch-immune flag.
- The spec's dash window text does not hold as written. A dash started at 0.35 s ends at 0.60 s, when the lunge starts, so it covers nothing. The real window is about 0.25 s ending at contact (about 7 frames at 30 FPS). Where it sits depends on distance and hitbox sizes.
- Phase 1 may go to Build with no separate Plan. Its start is gated on the dash/hit invulnerability fix being verified.

**Art Director (handoff 17, spec `design/g001-telegraph-visuals.md`):**
- Spawn marker: reuse an existing effect if it passes the acceptance checks; otherwise a minimal contracting ring.
- Lunge Grub: a strip along the locked lane, filled over 0–0.35 s and solid with chevrons over 0.35–0.60 s. This committed stage is tied to the spec 4.1 dash window.
- Fan Spitter: three thin rays at −25°, 0°, +25° with dashed growth until 0.40 s, then solid until fire at 0.60 s.
- No gameplay timing change is needed. All telegraphs already exceed the 0.5 s minimum.

## Findings

Questions for you (from handoff 16 and 17). You decide these; they are player-facing rules.

1. **Flinch on Phase 2 enemies.** Should a player hit leave Lunge Grub wind-up and lunge uninterrupted? Should a hit during recovery be ignored, or end recovery early? The same question applies to the Fan Spitter charge. The TD's default is flinch-immune during wind-up, lunge and recovery.
2. **Contact damage by state.** Does a Lunge Grub bite on contact during recovery or wind-up? The TD proposes damage only during the lunge and normal Chase.
3. **Dash window.** Either correct the spec 4.1 text and the criterion 2 check to the real timing (about 0.25 s ending at contact), or change the lunge or dash timing so the intended window holds. Hitbox sizes and speeds are not yet known. A report of those values has been requested from the engineer in handoff 18. Write the rule so that it holds whatever those values are (for example, expressed relative to contact), or mark the values that need the report as "confirm after the report".
4. **Fan Spitter.** Confirm the fan over the repositioning Spitter.
5. If the dash window or the wind-up sub-stages change, say so explicitly in the spec, so that the Studio can ask the Art Director to realign the 0.35 s committed-stage visual.

Also: say whether the Phase 2 acceptance criteria need any new player-observable checks because of the flinch decision, the Phase 2 telegraphs (art acceptance checks A1–A12) and the identity-at-rest art. If cost or readability forces you to drop a variant, say so; the Art Director's visual section for it is dropped with it.

## Decisions already made

- D-002: B (encounter escalation) first, then A (enemy behaviors); C in reserve. 5 rooms and 15–20 minute runs stay.

- If a choice would change the scope, a pillar or an Owner-made Decision, hand back with outcome `question` instead of deciding.

The five items above.

# G-001: Improve monotonous combat

## Owner request

> 戦闘が単調なので改善したい

## Interpretation

Success condition (qualitative): a player from the project's player profile experiences combat in the current build as varied and engaging rather than repetitive. Playing a run involves meaningful moment-to-moment variation in how the player positions, times and responds to enemies. Numeric thresholds belong to Design; the final verdict belongs to Review.

Constraints that shape any solution:
- Pillar 1 and D-001: combat stays one-button (attack + dash). No new input buttons without Owner approval. Variety must come from positioning, timing and enemy behavior.
- Readable threats (pillar 3) and 30/60 FPS correctness must be preserved.
- Small team: prefer reusing existing systems.

Out of scope: new input buttons or a larger player kit, changes to run length, new biomes or rooms unrelated to combat variety, and non-combat systems.

Not an immediate escalation: the Goal does not conflict with the vision or D-001. It must be solved inside them. If Diagnose finds that the only viable fixes need a new button or change a pillar, that triggers an Owner escalation then.

## Unknowns

Entry questions from `development-loop.md`:
- Observe: has the problem been observed first-hand? No. It is an experience problem (the game may work as specified but feel wrong), so `playtester` observes. The Owner's wording is not given to the Playtester, to avoid confirming a hypothesis.
- Diagnose: is the cause understood? No. What makes the combat feel monotonous is unknown (enemy behavior, kit depth, room design, pacing). Stage created.
- Decide: is there a real choice of direction, priority or scope? Yes. The diagnosis (handoff 04) offered three options (A: enemy behaviors, B: encounter design and escalation, C: rule rewards). Answered by D-002 (B first, then A; C in reserve).
- Design: is the intended behavior specified well enough to build? Not for the chosen direction. Done for Phase 1 and as proposals for Phase 2 (handoff 11, `design/g001-combat-escalation.md`). Phase 2 needs adjustment after the Plan and art answers (step 5c).
- Plan: needed for Phase 2 (feasibility and cost). Answered in handoff 16 and D-004: feasible and cheap. Phase 1 needs no separate Plan (handoff 16).
- Build: the dash-damage defect fix (done, handoff 08; one case still to make observable, step 3c), then Phase 1 and Phase 2 of the chosen direction.
- Verify: always after Build.
- Play: the Goal is about how the game feels, so a Playtester re-evaluates after each phase (fresh Handoff composed by the Studio without implementation history). It should record real-time run length and per-room clear time.
- Review: experience Goal, so the Game Director judges the outcome. Planned.
- Observe (defect): the Playtester saw a possible dash-damage defect. QA confirmed it against `design/combat.md` (handoff 05). Intended behavior is already specified, so the fix needed no Design or Plan.

Skipped: none.
