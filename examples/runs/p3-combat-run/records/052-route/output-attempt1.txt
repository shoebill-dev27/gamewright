### A. Look change (Art Director's decision; handoff 45)

Apply to the arrival ring (spawn marker) only:

1. **Dot, last phase.** From 0.6 s to 0.8 s the centre dot is amber `#FFC14D` at full brightness. No tint toward white or blue. Any glow around the dot uses only `#FFC14D` or `#FF5A1F`. Before 0.6 s the dot stays dim amber as built.
2. **Unchanged:** ring colour `#FF5A1F`; the timings (solid phase from 0.6 s, burst at 0.8 s); the ring's size and shape; all rules.

State these four statements in your change, in this wording. They go into the build description. For each, say whether the existing behavior already matched (documentation only) or you changed it:

- **S0:** "In the last 0.2 s (0.6 to 0.8 s) the dot is amber `#FFC14D` at full brightness." This replaces "hot, near-white core colour".
- **S1:** "The ring and its dot are drawn self-lit and do not depend on the lantern's light. At 0.0 s the ring's brightness is at least 40% of its brightness at 0.6–0.8 s."
- **S2:** "The 0.8 s burst uses only `#FF5A1F` and `#FFC14D`. It contains no white, near-white or cold-white element."
- **S3:** "Rings are outlines with no fill. Where two rings overlap or touch, brightness does not add above a single ring's peak, and each ring keeps its own dot."

If the existing look differs from S1–S3, making it match is part of this change.

### B. Clarifications (Game Designer's amended spec; handoff 44, D-009)

No new behavior is requested. Confirm each point against the code, state it in the build description, and say "matches" or "differs":

- **(d) Existing values (spec 3.8).** State each of the following that you can read from the repository or code notes, or write "not available": Grub speed, player speed, projectile speed and range, hearts, room size, hitbox sizes. Do not invent values.

# G-001: Improve monotonous combat

## Owner request

> 戦闘が単調なので改善したい

## Interpretation

Success condition (qualitative): a player from the project's player profile experiences combat in the current build as varied and engaging rather than repetitive. Playing a run involves meaningful moment-to-moment variation in how the player positions, times and responds to enemies. Numeric thresholds belong to Design; the final verdict belongs to Review.

Constraints that shape any solution:
- Pillar 1 and D-001: combat stays one-button (attack + dash). No new input buttons without Owner approval. Variety must come from positioning, timing and enemy behavior.
- Readable threats (pillar 3) and 30/60 FPS correctness must be preserved.
- Small team: prefer reusing existing systems.

Out of scope: new input buttons or a larger player kit, changes to run length, new biomes or rooms unrelated to combat variety, and non-combat systems.

Not an immediate escalation: the Goal does not conflict with the vision or D-001. It must be solved inside them. If Diagnose finds that the only viable fixes need a new button or change a pillar, that triggers an Owner escalation then.

## Unknowns

Entry questions from `development-loop.md`:
- Observe: has the problem been observed first-hand? No. It is an experience problem (the game may work as specified but feel wrong), so `playtester` observes. The Owner's wording is not given to the Playtester, to avoid confirming a hypothesis.

- Decide: is there a real choice of direction, priority or scope? Yes. The diagnosis (handoff 04) offered three options (A: enemy behaviors, B: encounter design and escalation, C: rule rewards). Answered by D-002 (B first, then A; C in reserve).

Done for Phase 1 and for Phase 2 (handoff 11, `design/g001-combat-escalation.md`, adjusted in handoff 22 and D-005).
