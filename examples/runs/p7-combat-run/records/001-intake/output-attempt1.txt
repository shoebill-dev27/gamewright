# G-001: Combat feels monotonous

## Owner request

> 戦闘が単調なので改善したい

## Interpretation

Success condition (qualitative): a player playing the current build's combat experiences it as varied and engaging instead of monotonous. Different situations call for noticeably different play (positioning, timing, use of attack and dash), and the player can tell why. The improvement stays inside the vision pillars: one-button combat (attack + dash only, D-001), short runs, readable threats. Numeric thresholds belong to Design; the final verdict belongs to Review.

Out of scope: new input buttons (needs Owner approval per D-001), changing run length, new biomes or content unrelated to combat variety, and any change to the core concept. Not a defect report: nothing in the request says combat is broken.

## Unknowns

- Observe: what exactly makes combat feel monotonous when played has not been observed first-hand. The cause is unknown (enemy behavior? repetitive optimal action? low pressure? room structure?). Stage: Observe (`playtester`), planned.
- Diagnose: cause not understood. Stage: Diagnose (`game-designer`), planned. Reads `design/combat.md` and the observations.
- Decide: tentative. Needed only if the diagnosis offers a real choice of direction or scope, or if a fix would touch D-001 or a pillar (then possible Owner escalation).
- Design: planned. Improved player-facing combat behavior is not specified anywhere; it needs a spec with player-observable acceptance criteria once the cause is known.
- Plan: tentative. Needed only if the spec's technical approach is non-obvious, risky or cross-system. Constraints: 30 and 60 FPS, reuse of existing systems.
- Build: planned (`gameplay-engineer`), the game must change. Verify (`qa`) planned after Build; add `art-director` in parallel if the change affects visuals.
- Play: planned. This is an experience Goal; a fresh playtester judges the result without implementation history.
- Review: planned (`game-director`), experience Goal.
- Skipped: none. Nothing in the Project Context answers any of these questions.

Play the current build as a player, with a focus on combat, across the available rooms and both enemy types. Report what you observe and experience as a player.

## Context

The Owner asked for a first-hand player observation of the game's combat. Nothing is known about expected results; report only what you experience.

## Findings

None. This Handoff deliberately carries no implementation information.

## Decisions already made

None.

## Constraints

- Play only through the player-visible view (`run_play`) and the player-facing manual (`repo/manual.md`). Use only the controls the manual describes.
- Play with a gamepad-style mindset: the player profile is an action player who likes dodging and spacing, and dislikes memorizing combo lists.
- Report observable experience only (what you saw, did, felt, and when). Do not speculate about code or internals.

None.

An observation report (per the `playtest-session` skill), covering: what you did over the session, how combat felt over time, moments of engagement or boredom, what you did repeatedly, and what, if anything, you wanted to do but couldn't.
